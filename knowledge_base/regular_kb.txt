### Funnel stages handled by this table:
Fresh, Pre Application, Initial Counselling Completed, NotInterested (before application)
**L2 counsellor (`assigned_counsellor_id`) owns all stages in this table.**

### Stages handled by `course_status_journeys` table:
Application (form submitted / walkin / exam / offer letter / ready for admission), Admission, Document Pending, Document Submitted, Enrolled, NotInterested (after application)
**L3 counsellor (`assigned_counsellor_l3_id`) owns all stages in this table.**

### Full funnel order (Regular LMS):
Fresh → Pre Application → Initial Counselling Completed → [L3 takes over] → Application (Form Submitted) → Exam/Interview → Offer Letter → Ready For Admission → Admission → Document Pending → Document Submitted → Enrolled

### Business rules:
- `current_student_status` covers early funnel stages: Fresh, Pre Application, Initial Counselling Completed, and NotInterested (before application). These are owned by **L2** (`assigned_counsellor_id`).
- `current_student_ni_sub_status` gives the sub-reason for NI. Use this column ONLY when the query asks for NI breakdown by reason, NI category, or why students went NI. Always filter `current_student_status = 'NotInterested'` .
- For Application, Admission, Document Pending, Document Submitted, Enrolled queries → use `course_status_journeys.course_status`. These are owned by **L3** (`assigned_counsellor_l3_id`).
- For university-specific queries: join path = `students → latest_course_statuses → university_courses`.
- `preferred_university` and `preferred_course` are PostgreSQL arrays — always use `ANY()`.
- Always use `COUNT(DISTINCT student_id)` after any JOIN, never `COUNT(*)`.

| Column | Type | Notes |
|--------|------|-------|
| remark_id | INTEGER PK | Use for counting remarks and DISTINCT ON. |
| student_id | VARCHAR → students | |
| counsellor_id | VARCHAR → counsellors | Counsellor who made the call. |
| calling_status | VARCHAR | 'Connected' or 'Not Connected'. |
| sub_calling_status | VARCHAR | Connected: 'Cold'. Not Connected: 'Ringing no response', 'Line Busy', 'Switched off', 'Invalid Number'|

| updated_at | TIMESTAMPTZ | When record was last updated (UTC). |

### Business rules:
- Raw connection = `calling_status = 'Connected'` only.
- Success rate / call performance / efficiency = `COUNT(Connected)/COUNT(all)` — NOT student conversion.
- First call per student: `ROW_NUMBER() OVER (PARTITION BY student_id ORDER BY created_at, remark_id) = 1`.
- Latest remark per student: `DISTINCT ON (student_id) ORDER BY student_id, created_at DESC`.
- Overdue callbacks: `callback_date < CURRENT_DATE`. Upcoming: `callback_date >= CURRENT_DATE`.
- Count callbacks by `remark_id`, not `student_id`.

## TABLE: course_status_journeys
Full audit trail of every status change. One row per event, multiple per student-course.

| Column | Type | Notes |
|--------|------|-------|
| status_history_id | INTEGER PK | |
| student_id | VARCHAR → students | |
| course_id | VARCHAR → university_courses | |
| counsellor_id | VARCHAR → counsellors | |
| course_status | VARCHAR | Status at this point in time. |
| deposit_amount | NUMERIC | Amount paid (0 if not a payment event). |
| currency | VARCHAR | Default 'INR'. |
| exam_interview_date | TIMESTAMPTZ | Exam/interview date if applicable. |
| event_time | TIMESTAMPTZ | Scheduled future event date; meaning depends on `course_status` — see event_time semantics below. |
| last_admission_date | TIMESTAMPTZ | Last date to complete admission. |
| notes | TEXT | Counsellor notes. |
| fee_type | VARCHAR | Known values:`'Annual Paid'`, `'Semester Paid'`, `'Semester fee paid'`, `'partial paid'`, `'Partially Paid'`, `'Partial Done'`, `'Registration done'`, `'one year fee paid'`, `'1st Year Fee Paid'`, `'full fee paid'`. |
| enrollment_counsellor_id | VARCHAR | Counsellor at enrollment stage. |
| created_at | TIMESTAMPTZ | When status change occurred (UTC). |
| updated_at | TIMESTAMPTZ | When record was last updated (UTC). |

### Business rules:
- **Primary table for Application, Admission, Document Pending, Document Submitted, Enrolled, and NotInterested (after application) queries.** Use `course_status` column.
- **This table is owned by L3 counsellors (`assigned_counsellor_l3_id`).** Use `course_status_journeys.counsellor_id` or join via `students.assigned_counsellor_l3_id` for L3-level queries.
- When user asks "form filled" / "form fills" / "applied" / "walkin" / "exam scheduled" / "offer letter" / "ready for admission" → query `course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission')` from this table. These are the application-stage statuses for the Regular LMS.
- When user asks "admitted" / "got admission" → query `course_status = 'Admission'` from this table. **ALWAYS exclude partial-payment rows:** add `AND ( fee_type NOT IN ('partial paid', 'Partially Paid', 'Partial Done'))`. These are partial fee events logged under Admission status, not actual admissions.
- When user asks "document pending" / "docs pending" → query `course_status = 'Document Pending'` from this table.
- When user asks "document submitted" / "docs submitted" → query `course_status = 'Document Submitted'` from this table.
- When user asks "enrolled" → query `course_status = 'Enrolled'` from this table.
- NotInterested after application → `course_status = 'NotInterested'` from this table.
- No "Shortlisted" status exists in this table — for shortlisted queries use `latest_course_statuses.is_shortlisted`.
- Latest per student-course: `DISTINCT ON (student_id, course_id) ORDER BY student_id, course_id, created_at DESC`.
- Total fees collected: `SUM(deposit_amount) WHERE deposit_amount > 0`.

### Application-stage statuses (Regular LMS — course_status_journeys):
The following `course_status` values all indicate a student has "applied" / "filled the form" in the Regular LMS:
- `'Form Submitted – Portal Pending'` — form submitted, awaiting portal processing
- `'Form Submitted – Completed'` — form submitted and portal processing complete
- `'Walkin Completed'` — student **has walked in** to the institution (walkin happened) → **counts as application**
- `'Exam/Interview Scheduled'` — exam or interview has been scheduled
- `'Offer Letter/Results Pending'` — awaiting offer letter or exam results
- `'Offer Letter/Results Released'` — offer letter or results have been released
- `'Ready For Admission'` — student is ready to proceed with admission

**CRITICAL:** In the Regular LMS, `course_status = 'Application'` does NOT exist. NEVER query `course_status = 'Application'` for Regular LMS. Always use the IN list above when the user asks about form filled / applications.

### Walkin Scheduled vs Walkin Completed — CRITICAL DISTINCTION:
- `'Walkin Scheduled'` — counsellor has **scheduled** a walkin; student is **going to** visit the college. This is a **pre-application** status. **NOT counted as an application. NEVER include in the application IN list.**
- `'Walkin Completed'` — student **has actually walked in** to the college. This IS an application. Always include in the application IN list.

**Rule:** When the user asks about "walkin" without further qualifier, count only `'Walkin Completed'` (application stage). If the user explicitly asks about "walkin scheduled" or "upcoming walkins", use `course_status = 'Walkin Scheduled'` — but NEVER include it in application counts.

### event_time — Semantics per course_status:
`event_time` stores the scheduled/expected date for the next milestone event. Its meaning varies by `course_status`:

| course_status | event_time meaning |
|---|---|
| `'Walkin Scheduled'` | Date/time the walkin is planned to happen |
| `'Exam/Interview Scheduled'` | Date/time of the scheduled exam or interview |
| `'Offer Letter/Results Pending'` | Expected date of receiving the offer letter / results |
| `'Offer Letter/Results Released'` | Date the offer letter / results were released |
| Other statuses | May be NULL or not applicable |

**Rules for event_time:**
- Use `event_time` when the user asks "when is the walkin", "walkin date", "exam date", "interview date", "when will offer letter come", "offer letter expected date".
- Always convert `event_time` to IST using `AT TIME ZONE 'Asia/Kolkata'` before displaying.
- NEVER confuse `event_time` with `created_at` — `created_at` is when the status row was logged; `event_time` is the future event being tracked.

## DISTINCTION 8 — "Interest" vs "Preference" vs "Shortlisted"

| User asks... | Table | Logic |
|---|---|---|
| "Students interested in [course]" / "course interest" / "how many students are interested" | `course_status_journeys` | `COUNT(DISTINCT student_id)` for that course_id — students who have taken action on this course |
| "Students who prefer/stated [course]" / "student preference" | `students.preferred_course` | `'Course Name' = ANY(preferred_course)` — student's self-declared preference at lead capture |
| "Shortlisted courses" / "courses shortlisted by counsellor" | `latest_course_statuses` | `is_shortlisted = true` — counsellor-flagged serious options |

**Key rule:** 
- **Interest** = action taken (student has a record in `course_status_journeys` for that course).
- **Preference** = stated intent (student declared it in `preferred_course` array at lead capture).
- **Shortlisted** = counsellor flagged (counsellor marked `is_shortlisted = true` in `latest_course_statuses`).

**CRITICAL:**
- NEVER use `latest_course_statuses` for general "interest" queries — it is ONLY for shortlisted courses and API status tracking.
- NEVER use `students.preferred_course` for "interest" metrics — it's only for self-stated preferences before counsellor interaction.
- For "which courses have most interest" / "student interest by course" → ALWAYS use `course_status_journeys`.
- NEVER look for "Shortlisted" status in `course_status_journeys` — that table has no shortlisted concept. Always use `latest_course_statuses.is_shortlisted`.

## DISTINCTION 9 — NotInterested (NI)

### Three NI Variants — Quick Reference

| Term | Meaning | Primary table | Trigger phrase |
|------|---------|--------------|----------------|
| **Total NI** | All students currently NI (before OR after application) | `students` UNION `course_status_journeys` | "total NI", "how many NI", "NI count" |
| **Pre-NI** | NI students who never had ICC and never reached Application/Admission/etc. | `students` with `"first_Icc_Date" IS NULL` + NOT IN progression | "pre NI", "NI with no ICC", "NI who never progressed" |
| **First NI** | NI students whose **first remark** falls in the date window (earliest contact) | `student_remarks` DISTINCT ON `created_at ASC` for current NI students | "first NI", "first time NI", "newly NI" |

**NEVER mix these up.** Total NI ≠ Pre-NI ≠ First NI. Always confirm which variant the user means before generating SQL.

---

### NI-1 — Pure NI before application (student never applied)
Use when: "NI before application", "NI who never applied", "NI who dropped before applying"
```sql
SELECT COUNT(DISTINCT student_id) FROM students
WHERE current_student_status = 'NotInterested';
```

### NI-2 — Pure NI after application (course-level NI)
Use when: "NI after application", "NI who applied to a course and backed out"
```sql
SELECT COUNT(DISTINCT student_id) FROM course_status_journeys
WHERE course_status = 'NotInterested'
AND student_id IN (SELECT student_id FROM students);
```

### NI-3 — General NI (no context given)
Use when: user just says "total NI", "how many NI students" with no further qualifier.
ALWAYS use BOTH tables and return `COUNT(DISTINCT student_id)` combining results:

**All-time total NI:**
```sql
SELECT COUNT(DISTINCT student_id) AS total_ni FROM (
    SELECT student_id FROM students WHERE current_student_status = 'NotInterested'
    UNION
    SELECT student_id FROM course_status_journeys
    WHERE course_status = 'NotInterested'
    AND student_id IN (SELECT student_id FROM students)
) combined;
```

**Date-filtered total NI (use `updated_at` on both tables):**
```sql
SELECT COUNT(DISTINCT student_id) AS total_ni FROM (
    SELECT student_id FROM students
    WHERE current_student_status = 'NotInterested'
      AND updated_at >= <start_ist>
      AND updated_at <  <end_ist>
    UNION
    SELECT student_id FROM course_status_journeys
    WHERE course_status = 'NotInterested'
      AND student_id IN (SELECT student_id FROM students)
      AND created_at >= <start_ist>
      AND created_at <  <end_ist>
) combined;
```
Apply standard IST date window (see TIMEZONE RULES).
- `students` branch → use `updated_at` (tracks when the NI status was last SET on the student record).
- `course_status_journeys` branch → use `created_at` (append-only log; each row's `created_at` IS the event timestamp).

### NI-4 — NI students at a specific funnel stage
Use when: "NI students who are at [stage]", "NI students marked as [stage]", "NI students currently at [stage]".
NEVER query both NI and stage from the same students table — they cannot coexist on the same row.

- Stage from `students` table (Fresh, Pre Application, ICC) → subquery on `students.current_student_status`
- Stage from `course_status_journeys` (Application, Admission, Document Pending, Document Submitted, Enrolled) → subquery on `course_status_journeys.course_status`

```sql
-- Stage from students table (e.g. Pre Application, ICC, Fresh):
SELECT COUNT(DISTINCT student_id) FROM course_status_journeys
WHERE course_status = 'NotInterested'
AND student_id IN (
    SELECT student_id FROM students WHERE current_student_status = '[stage]'
);

-- Stage from course_status_journeys (e.g. Application, Admission):
SELECT COUNT(DISTINCT student_id) FROM course_status_journeys
WHERE course_status = 'NotInterested'
AND student_id IN (
    SELECT student_id FROM course_status_journeys WHERE course_status = '[stage]'
);
```

### NI-6 — Pre-NI Students (NI with no ICC and never progressed to application or beyond)
Use when: "pre NI", "NI students who never had ICC", "NI who never applied", "NI with no progress"
Definition: Students who are `NotInterested`, never had an ICC (`"first_Icc_Date" IS NULL`), and never reached Application/Admission/Document Pending/Document Submitted/Enrolled.
```sql
WITH never_progressed AS (
    SELECT s.student_id
    FROM students s
    WHERE s.current_student_status = 'NotInterested'

      AND s.student_id NOT IN (
```

### NI-7 — First NI (NI students whose first remark falls in the date window)

## DISTINCTION 10 — Fee Column Selection

**CRITICAL: There are two different fee concepts — course fee and payment collected. Never confuse them.**

| User asks about... | Table | Column | Notes |
|---|---|---|---|
| Total fee of a course / admission fee / course worth / how much does a course cost / fee structure | `university_courses` | `total_fees` | Full course price from the catalog |
| Per-semester fee | `university_courses` | `semester_fees` | |
| Per-year fee | `university_courses` | `annual_fees` | |
| Deposit paid / amount deposited / payment collected / fees received from a student | `course_status_journeys` | `deposit_amount` | Actual money paid by student |
| Total fees collected / revenue | `course_status_journeys` | `SUM(deposit_amount) WHERE deposit_amount > 0` | |

**Rules:**
- "Total fee", "admission fee", "course fee", "how much does a course cost", "course worth", "fee of [course/university]" → ALWAYS use `university_courses.total_fees`.
- "Deposit", "deposit amount", "amount paid", "payment collected", "fees received" → ALWAYS use `course_status_journeys.deposit_amount`.
- NEVER use `deposit_amount` to answer questions about course pricing — it is actual money paid, not the listed course fee.
- NEVER use `total_fees` to answer questions about payments collected — it is the catalog price, not actual collected amount.

## DISTINCTION 11 - DEPOSIT AMOUNT — CRITICAL RULES

---

### RULE D1 — Never SUM deposit_amount without dedup CTE

`course_status_journeys` is append-only. Same payment gets logged multiple times via re-triggers. Always use this CTE before any `SUM(deposit_amount)`:

```sql
deduped_payments AS (
    SELECT DISTINCT ON (student_id, course_id, fee_type, created_at::DATE)
        student_id, course_id, deposit_amount,
        INITCAP(TRIM(fee_type)) AS fee_type_clean
    FROM course_status_journeys
    WHERE deposit_amount > 0
      AND student_id IN (SELECT student_id FROM students)
    ORDER BY student_id, course_id, fee_type, created_at::DATE, created_at DESC
)
```

`created_at DESC` ensures if the same fee_type is corrected on the same day, the latest (corrected) amount wins. Do NOT include `deposit_amount` in the `DISTINCT ON` key — that breaks correction handling.

---

### RULE D2 — Two separate de-dups in one query

Admission de-dup and payment de-dup are independent problems:

- **Admission** → `MIN(created_at)` per `(student_id, course_id)`
- **Payment** → `DISTINCT ON (student_id, course_id, fee_type, created_at::DATE) ORDER BY ... created_at DESC`

Never use one strategy for both.

---

### RULE D3 — Always normalize fee_type

Always apply `INITCAP(TRIM(fee_type))` when reading from `course_status_journeys`. Never aggregate or filter raw `fee_type`.

Known normalized values: `Semester Paid`, `Full Fee Paid`, `Annual Paid`, `Semester Fee Paid`, `Registration Done`, `Partially Paid`, `Partial Done`, `One Year Fee Paid`, `1St Year Fee Paid`.

---

### RULE D4 — fee_type breakdown always in pivot format

Never use `STRING_AGG` for fee type breakdown. Always use `COUNT(DISTINCT CASE WHEN ...)` per fee type as separate columns — same pattern as stage breakdown (RULE O2).

---

### PATTERN — Fee summary (canonical base template)

```sql
WITH admitted_students AS (
    SELECT student_id, course_id, MIN(created_at) AS first_admission_date
    FROM course_status_journeys
    WHERE course_status = 'Admission'
      AND student_id IN (SELECT student_id FROM students)
    GROUP BY student_id, course_id
),
deduped_payments AS (
    SELECT DISTINCT ON (student_id, course_id, fee_type, created_at::DATE)
        student_id, course_id, deposit_amount,
        INITCAP(TRIM(fee_type)) AS fee_type_clean
    FROM course_status_journeys
    WHERE deposit_amount > 0
      AND student_id IN (SELECT student_id FROM students)
    ORDER BY student_id, course_id, fee_type, created_at::DATE, created_at DESC
),
payments AS (
    SELECT student_id, course_id, SUM(deposit_amount) AS total_deposit_collected
    FROM deduped_payments
    GROUP BY student_id, course_id
)
SELECT
    uc.university_name,
    COUNT(DISTINCT adm.student_id)                                    AS total_admitted_students,
    SUM(uc.total_fees)                                                AS total_course_worth,
    COALESCE(SUM(p.total_deposit_collected), 0)                       AS total_deposit_collected,
    SUM(uc.total_fees) - COALESCE(SUM(p.total_deposit_collected), 0)  AS total_fee_remaining,
    COUNT(DISTINCT CASE WHEN dp.fee_type_clean = 'Semester Paid'     THEN dp.student_id END) AS semester_paid,
    COUNT(DISTINCT CASE WHEN dp.fee_type_clean = 'Full Fee Paid'     THEN dp.student_id END) AS full_fee_paid,
    COUNT(DISTINCT CASE WHEN dp.fee_type_clean = 'Annual Paid'       THEN dp.student_id END) AS annual_paid,
    COUNT(DISTINCT CASE WHEN dp.fee_type_clean = 'Semester Fee Paid' THEN dp.student_id END) AS semester_fee_paid,
    COUNT(DISTINCT CASE WHEN dp.fee_type_clean = 'Registration Done' THEN dp.student_id END) AS registration_done,
    COUNT(DISTINCT CASE WHEN dp.fee_type_clean = 'Partially Paid'    THEN dp.student_id END) AS partially_paid,
    COUNT(DISTINCT CASE WHEN dp.fee_type_clean = 'Partial Done'      THEN dp.student_id END) AS partial_done,
    COUNT(DISTINCT CASE WHEN dp.fee_type_clean = 'One Year Fee Paid' THEN dp.student_id END) AS one_year_fee_paid,
    COUNT(DISTINCT CASE WHEN dp.fee_type_clean = '1St Year Fee Paid' THEN dp.student_id END) AS first_year_fee_paid
FROM admitted_students adm
JOIN university_courses uc ON adm.course_id = uc.course_id
LEFT JOIN payments p  ON adm.student_id = p.student_id  AND adm.course_id = p.course_id
LEFT JOIN deduped_payments dp ON adm.student_id = dp.student_id AND adm.course_id = dp.course_id
GROUP BY uc.university_name
ORDER BY total_deposit_collected DESC;
```

Adapt grouping: university → `GROUP BY uc.university_name`, course → add `uc.course_name`, counsellor → join via `students.enrollment_counsellor_id`.

### PATTERN 1 — Funnel breakdown (UNION ALL, never GROUP BY)

Early stages from `students`, later stages from `course_status_journeys`:

```sql
SELECT 'Total Leads' AS stage, COUNT(DISTINCT student_id) AS count FROM students

UNION ALL

UNION ALL
```

### PATTERN 2 — Stage breakdown per entity (wide/pivot format)

One row per entity, one column per stage. NEVER long format.

### PATTERN 3 — Counsellor call performance (LEFT JOIN always)

```sql
SELECT
    c.counsellor_name,
    COUNT(sr.remark_id) AS total_calls,
    COUNT(CASE WHEN sr.calling_status = 'Connected' THEN 1 END) AS connected_calls,
    ROUND(
        COUNT(CASE WHEN sr.calling_status = 'Connected' THEN 1 END) * 100.0 /
        NULLIF(COUNT(sr.remark_id), 0), 2
    ) AS success_rate
FROM counsellors c
LEFT JOIN student_remarks sr ON c.counsellor_id = sr.counsellor_id
GROUP BY c.counsellor_id, c.counsellor_name
HAVING COUNT(sr.remark_id) > 0
ORDER BY success_rate DESC;
```

### PATTERN 4 — Team call performance

Team queries ALWAYS require: `manager → team_member (counsellors self-join) → student_remarks`. NEVER join students table for call metrics. ALWAYS include `WHERE manager.role = 'to'`.

```sql
SELECT
    manager.counsellor_name AS team_owner,
    COUNT(sr.remark_id) AS total_calls,
```

### PATTERN 6 — Benchmark / above-average comparison

```sql
WITH metrics AS (
    SELECT
        c.counsellor_id, c.counsellor_name,
        COUNT(sr.remark_id) AS total_calls,
        ROUND(COUNT(CASE WHEN sr.calling_status = 'Connected' THEN 1 END) * 100.0 /
              NULLIF(COUNT(sr.remark_id), 0), 2) AS success_rate
    FROM counsellors c
    LEFT JOIN student_remarks sr ON c.counsellor_id = sr.counsellor_id
    GROUP BY c.counsellor_id, c.counsellor_name
    HAVING COUNT(sr.remark_id) > 0
),
benchmark AS (
    SELECT AVG(success_rate) AS avg_rate, STDDEV(success_rate) AS stddev_rate FROM metrics
)
SELECT
    m.*, b.avg_rate AS benchmark_avg,
    CASE WHEN m.success_rate > b.avg_rate THEN 'Above Average'
         WHEN m.success_rate < b.avg_rate THEN 'Below Average'
         ELSE 'Average' END AS category
FROM metrics m CROSS JOIN benchmark b
ORDER BY m.success_rate DESC;
```

### PATTERN 8 — University deduplication (student at highest stage)

When a student has multiple courses at the same university, assign their highest stage using `course_status_journeys`:

```sql
WITH stage_priority AS (
    SELECT
        uc.university_name, csj.student_id,
        CASE
            WHEN csj.course_status = 'Enrolled'           THEN 6
            WHEN csj.course_status = 'Document Submitted' THEN 5
            WHEN csj.course_status = 'Document Pending'   THEN 4
            WHEN csj.course_status = 'Admission'          THEN 3
            WHEN csj.course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission') THEN 2
            ELSE 0
        END AS stage_rank
    FROM university_courses uc
    JOIN course_status_journeys csj ON uc.course_id = csj.course_id
),
final_stage AS (
    SELECT university_name, student_id, MAX(stage_rank) AS final_rank
    FROM stage_priority GROUP BY university_name, student_id
)
SELECT
    university_name,
    COUNT(*) FILTER (WHERE final_rank = 2) AS applications,
    COUNT(*) FILTER (WHERE final_rank = 3) AS admissions,
    COUNT(*) FILTER (WHERE final_rank = 4) AS document_pending,
    COUNT(*) FILTER (WHERE final_rank = 5) AS document_submitted,
    COUNT(*) FILTER (WHERE final_rank = 6) AS enrolled
FROM final_stage
GROUP BY university_name ORDER BY admissions DESC;
```

### PATTERN 11 — Date-filtered count from course_status_journeys (ANY status)

Use this for ALL queries like for "for all admission/enrolled/application/document_pending/document_submitted" related queries like "admitted in last N days", "enrolled this month", "applications this week", etc.
Always wrap in a subquery with `MIN(created_at)` per student to get their first event date, then apply the IST-adjusted date filter.

```sql
SELECT COUNT(DISTINCT student_id) AS count
FROM (
    SELECT student_id, MIN(created_at) AS first_event_date
    FROM course_status_journeys
    WHERE course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission')
      AND student_id IN (SELECT student_id FROM students)
    GROUP BY student_id
) sub
WHERE first_event_date >= CURRENT_DATE - interval 'N days' - interval '5 hours 30 minutes'
  AND first_event_date <  CURRENT_DATE + interval '1 day'  - interval '5 hours 30 minutes';
```

**Applies to all statuses:** application-stage IN list (Form Submitted – Portal Pending / Completed, Walkin Completed, Exam/Interview Scheduled, Offer Letter/Results Pending/Released, Ready For Admission), `'Admission'`, `'Document Pending'`, `'Document Submitted'`, `'Enrolled'`, `'NotInterested'` (after application).
**Why MIN?** `course_status_journeys` is append-only — a student can have multiple rows for the same `course_status` (re-triggers, duplicates). Without MIN, duplicates inflate counts and old students reappear in recent-period filters.

### PATTERN 9 — Conversion rate from application to admission

Use `course_status_journeys` for both Application and Admission counts:

```sql
SELECT
    COUNT(DISTINCT CASE WHEN csj.course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission') THEN csj.student_id END) AS applications,

        COUNT(DISTINCT CASE WHEN csj.course_status = 'Admission' THEN csj.student_id END) * 100.0 /
        NULLIF(COUNT(DISTINCT CASE WHEN csj.course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission') THEN csj.student_id END), 0), 2
    ) AS conversion_rate
FROM course_status_journeys csj;
```

### PATTERN 10 — Individual vs Team comparison (UNION ALL)

When asked to compare individual counsellors vs teams, use UNION ALL with identical 5-column schema. Both parts must be per-entity (per counsellor / per team), never a single global average. NEVER add role filters on the individual half.

### PATTERN 12 — First Connected (total count + counsellor wise)

Counts students whose **very first Connected call** falls within a given date window. Uses `MIN(created_at)` to find each student's first connected event.
Apply the standard IST date window (see TIMEZONE RULES) for today / yesterday / last N days as needed.

**Total first connected (any date window):**
```sql

    SELECT 
        student_id,
        MIN(created_at) AS first_connected_at
    FROM student_remarks
    WHERE calling_status = 'Connected'
      AND student_id IN (SELECT student_id FROM students)
    GROUP BY student_id
)
SELECT COUNT(DISTINCT fcd.student_id) AS first_connected_count
FROM first_connected_dates fcd
WHERE fcd.first_connected_at >= <start_ist>   -- e.g. CURRENT_DATE - INTERVAL '1 day' - INTERVAL '5 hours 30 minutes'
  AND fcd.first_connected_at <  <end_ist>;    -- e.g. CURRENT_DATE - INTERVAL '5 hours 30 minutes'
```

**First connected counsellor wise (any date window):**
```sql
SELECT
    c.counsellor_name,
    COUNT(DISTINCT sr.student_id) AS first_connected_count
FROM student_remarks sr
JOIN counsellors c 
    ON c.counsellor_id = sr.counsellor_id
WHERE sr.calling_status = 'Connected'
  AND sr.student_id IN (SELECT student_id FROM students)
  AND sr.created_at = (
        SELECT MIN(sr2.created_at)

ORDER BY first_connected_count DESC;
```

**RULE J3 exception:** RULE J3 (`FROM counsellors LEFT JOIN student_remarks`) applies to full-roster call-metric queries. - Always include `HAVING COUNT(*) > 0`.
- Add `LIMIT 1` when asking for a single best/worst slot.

**RULE S9.** When a query must return BOTH a total count AND a filtered subset count for the same entity (e.g. total students AND admitted students per counsellor), use CASE WHEN inside COUNT. Using WHERE drops all non-matching rows, making the total count impossible.

Example: `COUNT(DISTINCT csj.student_id) AS total_students, COUNT(DISTINCT CASE WHEN csj.course_status = 'Admission' THEN csj.student_id END) AS admissions, COUNT(DISTINCT CASE WHEN csj.course_status = 'Document Pending' THEN csj.student_id END) AS document_pending`

**RULE S10.** "Spread across teams" / "distribution across teams" / "per team breakdown" means one row per team member (GROUP BY both manager AND team_member). It does NOT mean one aggregated row per team. If the question asks how something is distributed or spread, always include the member-level detail:
- Group by `manager.counsellor_id, manager.counsellor_name, team_member.counsellor_id, team_member.counsellor_name`

### JOIN RULES

**RULE J1.** When joining two counsellor FK columns, use two separate subqueries or determine L2 vs L3 from context. Use the following format:
```sql
ON c.counsellor_id = s.assigned_counsellor_id
```
or
```sql
ON c.counsellor_id = s.assigned_counsellor_l3_id
```
Do not combine these conditions with OR in a single JOIN.

**RULE J2.** NEVER filter by counsellor name on any base table. Always JOIN counsellors and use `c.counsellor_name ILIKE '%Name%'`.

**RULE J3.** When joining counsellors to student_remarks for call metrics, ALWAYS use LEFT JOIN.
```sql
FROM counsellors c LEFT JOIN student_remarks sr ON ...
```
This ensures that counsellors with zero calls are included in the results.
- Applies to: total calls, connected calls, success rate, efficiency, any call metric per counsellor.

**RULE J4.** For conversion rate queries (e.g. application → admission), use `course_status_journeys` with CASE WHEN for both counts in a single query (see Pattern 9).

**RULE J5.** When two counts are logically independent (come from different tables with no shared row context), NEVER join the tables to compute them together. Use correlated subqueries in SELECT or a CROSS JOIN of two single-row CTEs.

**RULE J6.** ALWAYS use `ILIKE '%Name%'` (with leading and trailing wildcards) when filtering by a person's name. NEVER use `ILIKE 'Name'` (no wildcards) — stored names include first+last name so an exact match will return zero rows.

**RULE J7.** When a query starts from a child table (`course_status_journeys`, `student_remarks`, `latest_course_statuses`, `student_lead_activities`) without JOINing `students`, ALWAYS add `WHERE student_id IN (SELECT student_id FROM students)` to guard against orphaned test-lead records that were deleted from `students` but remain in child tables. Failure to do this will inflate counts with invalid data.

**RULE J8.** **Preserve Outer Joins.** When using a `LEFT JOIN` to show a full roster (e.g., "all universities" or "all counsellors"), never put a filter for a child-table column in the `WHERE` clause. Put those filters inside the `ON` condition or use a `CASE WHEN` in the SELECT. Using `WHERE` on a `LEFT JOINED` table column will accidentally turn it into an `INNER JOIN` and hide entities with zero counts.

Example of correct LEFT JOIN preservation:
```sql
-- CORRECT: Filter in ON clause
FROM counsellors c
LEFT JOIN students s ON c.counsellor_id = s.assigned_counsellor_id 
    AND s.current_student_status = 'Pre Application'

-- WRONG: Filter in WHERE clause (turns LEFT JOIN into INNER JOIN)
FROM counsellors c
LEFT JOIN students s ON c.counsellor_id = s.assigned_counsellor_id
WHERE s.current_student_status = 'Pre Application'  -- This hides counsellors with no Pre Application students
```

### TIMEZONE RULES

All `created_at` columns store UTC. User expects IST (UTC+5:30). `CURRENT_DATE` is in IST.
**Case 1 — Explicit day boundary (today / yesterday / specific date):**
```sql
WHERE created_at >= (CURRENT_DATE - interval '5 hours 30 minutes')
  AND created_at <  (CURRENT_DATE + interval '1 day' - interval '5 hours 30 minutes')
```

**Case 2 — Rolling interval (last N days / months):**
```sql
WHERE created_at >= CURRENT_DATE - interval '30 days' - interval '5 hours 30 minutes'
  AND created_at <  CURRENT_DATE + interval '1 day' - interval '5 hours 30 minutes'
```
Always apply the `- interval '5 hours 30 minutes'` IST offset even for rolling intervals.

**Case 3 — `callback_date` column (type DATE):**
```sql
WHERE callback_date < CURRENT_DATE   -- overdue
WHERE callback_date >= CURRENT_DATE  -- upcoming
```
NEVER apply timezone offset to `callback_date`.

**Case 4 — Hour extraction (IST):**
```sql
EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Kolkata')
-- or equivalent:
EXTRACT(HOUR FROM (created_at + INTERVAL '5 hours 30 minutes'))
```

**RULE TZ1.** Always apply `- interval '5 hours 30 minutes'` IST offset to any `created_at` date boundary filter. No date filter = no timezone adjustment.

**RULE TZ2.** NEVER alter the user's specified time interval value. If the user asks for "last 6 months", write `INTERVAL '6 months'` exactly. Do NOT subtract timezone offset hours from a duration (e.g. do NOT write `INTERVAL '5 months 24 days'` instead of `INTERVAL '6 months'`). ALWAYS use `CURRENT_DATE - interval 'N ...' - interval '5 hours 30 minutes'` form — never `NOW() - INTERVAL 'N ...'`.

**RULE TZ3.** In PostgreSQL, a column alias defined in the SELECT clause cannot be used inside expressions, functions, or CASE statements in the ORDER BY clause. It can only be used directly.This limitation applies specifically when the alias is derived (computed via CASE, functions, etc.), not a physical column.If your ORDER BY logic becomes complex, using a subquery or CTE is the most maintainable and scalable approach.Relying on alias reuse in complex queries can lead to unexpected failures during migrations (e.g., MySQL → PostgreSQL), so avoid it in production-grade SQL.

**RULE TZ4.** Whenever a query returns a date or timestamp to the user, ALWAYS convert `created_at` or `updated_at` to IST using `AT TIME ZONE 'Asia/Kolkata'` (or equivalently `+ INTERVAL '5 hours 30 minutes'`). NEVER display raw UTC timestamps to the user. Additionally, ALWAYS use `MIN(created_at)` when selecting a representative date for an event from append-only tables (e.g. `course_status_journeys`, `student_remarks`) — never use `MAX` or a raw undeduped `created_at` for this purpose.
```sql
-- Correct: display date in IST
SELECT MIN(created_at) AT TIME ZONE 'Asia/Kolkata' AS event_date_ist
FROM course_status_journeys
WHERE course_status = '<Status>'
GROUP BY student_id;
```

# SECTION 7 — COMMON QUERY AMBIGUITIES (for MCQ disambiguation)

When generating clarifying questions for ambiguous queries, consider these patterns:

## Time Ambiguity (no date mentioned)
- Options: Today, This week, This month, This year, All time

## Counsellor Scope (mentions "counsellor" without qualifier)
- Options: All counsellors, Active counsellors only, L2 counsellors, L3 counsellors

## Student Funnel Stage (mentions "students" without stage)
- Options: All stages, Fresh leads only, Application+, Enrolled only

## Metric Type (mentions "performance" / "stats" / "report")
- Options: Count, Conversion rate, Average, Total sum

## Grouping (aggregation query without explicit GROUP BY)
- Options: Per counsellor, Per source, Per date, Per university, Total only

## NI Sub-status (mentions "not interested" without specifics)
- Options: All NI reasons, Budget issue, Not eligible, Already enrolled, Other reasons

## University / Course Scope
- Options: All universities, Specific university, Top universities by enrollment, Partner universities only
