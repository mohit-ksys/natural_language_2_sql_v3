### Funnel stages handled by this table:
Pre Application, Initial Counselling Completed, NotInterested (till application)
**L2 counsellor (`assigned_counsellor_id`) owns all stages in this table.**

### Stages handled by `course_status_journeys` table:
Application (form submitted / walkin / exam / offer letter), Admission, Document Pending, Document Submitted, Enrolled, NotInterested (after application)
**L3 counsellor (`assigned_counsellor_l3_id`) owns all stages in this table.**

### Full funnel order (Regular LMS):
Pre Application → Initial Counselling Completed →  Application (Form Submitted) →[L3 takes over] → Exam/Interview → Offer Letter → Admission → Document Pending → Document Submitted → Enrolled

### Business rules:
- `current_student_status` covers early funnel stages: Pre Application, Initial Counselling Completed, and NotInterested (before application). These are owned by **L2** (`assigned_counsellor_id`).
- `current_student_ni_sub_status` gives the sub-reason for NI. Use this column ONLY when the query asks for NI breakdown by reason, NI category, or why students went NI. Always filter `current_student_status = 'NotInterested'` .
- For Application, Admission, Document Pending, Document Submitted, Enrolled queries → use `course_status_journeys.course_status`. These are owned by **L3** (`assigned_counsellor_l3_id`).
- For university-specific queries: join path = `students → latest_course_statuses → university_courses`.
- `preferred_university`, `preferred_stream`, `preferred_degree`, `preferred_level`, `preferred_specialization`, `preferred_city`, `preferred_state` are PostgreSQL arrays — always use `ANY()`.
- Always use `COUNT(DISTINCT student_id)` after any JOIN, never `COUNT(*)`.'
- **"connected yet" / "has L2 connected" / "L2 ever connected" / "how many leads connected by L2"** → use `is_connected_yet = true` on `students`. NEVER use `student_remarks` for this.
- **"L3 connected yet" / "has L3 connected" / "L3 ever connected" / "how many students L3 connected to"** → use `is_connected_yet_l3 = true` on `students`. NEVER use `student_remarks` for this.
- **"not connected yet" / "L2 never connected"** → `is_connected_yet = false`. **"L3 never connected"** → `is_connected_yet_l3 = false`.
- Fresh leads are those leads which are not assigned yet or do not have any remark. 
- NEVER select current_student_status = 'Fresh' in any query unless the user explicitly asks for "total fresh right now" for this only you can select current_student_status = 'Fresh' , Fresh Leads are decided on run time they can only at a point of time not today, not yesterday and not for any month or year.
- If the query ask fresh leads today you must select the leads that came today ->
```SELECT COUNT(DISTINCT student_id) AS fresh_leads_count
FROM students
WHERE created_at >= CURRENT_DATE - INTERVAL '5 hours 30 minutes'
  AND created_at < CURRENT_DATE + INTERVAL '1 day' - INTERVAL '5 hours 30 minutes';
```
- If any query mentions fresh until and unless is "total fresh right now" then only select current_student_status = 'Fresh'.

### Counsellor Data Retrieval &Shift Definition Rules (Strict)

#### Counsellor Level Enforcement
- Critical Rules : Never I am saying never when asked for counsellor wise never all select columns 
- Always verify whether L3 counsellor data has been explicitly requested.
- If L3 is **not explicitly specified**, default to L2.
- Under no circumstances should L3 data be provided unless it is clearly and explicitly requested.
- When a user asks for a counsellor without specifying a level, **only provide L2 counsellor data**.

#### Shift Definition
- A counsellor’s shift is strictly defined by their activity within a given day.
- The **first remark** recorded by the counsellor on that day marks the **start of the shift**.
- The **last remark** recorded by the counsellor on that day marks the **end of the shift**.
- No other indicators should be used to determine shift boundaries.


### Counsellor FK selection:
- **RULE CNS-DEFAULT — "counsellor wise", "counsellor data", "counsellor breakdown", or ANY general per-counsellor query without an explicit level → ALWAYS use L2 only.** Join via `students.assigned_counsellor_id` and filter `counsellors.role = 'l2'`. This rule applies regardless of the metric being broken down (forms, admissions, leads, NI, etc.). Do NOT produce a UNION of L2 + L3. Do NOT add an L3 section. L2 is the first point of contact and the default owner of every lead.
- **RULE CNS-L3 — Only use L3 when the query explicitly says "L3", "l3 counsellor", or "admission counsellor".** In that case join via `course_status_journeys.assigned_l3_counsellor_id` and filter `counsellors.role = 'l3'`. NEVER mix L2 and L3 in the same output unless the user explicitly asks for both.
- **"counsellor wise lead assignment" / "leads assigned per counsellor" / "how many leads each counsellor has" / "lead count per counsellor"** → `COUNT(DISTINCT s.student_id)` from `students` grouped by `s.assigned_counsellor_id`, joined to `counsellors` filtering `c.role = 'l2'` and `c.status = 'active'`. There is NO `lead_assignment_log` table — NEVER invent or use it. The `counsellors.total_leads` column is a denormalized cache — do NOT use it for breakdowns; always query `students` directly.
- Pre-application queries (Pre Application, ICC, NI before application) → `students.assigned_counsellor_id` (L2)
- Application / admission queries (form filled, exam scheduled, offer letter) — for the DATA source use `course_status_journeys`; for the COUNSELLOR grouping dimension, still default to L2 (`students.assigned_counsellor_id`) unless L3 is explicitly requested. NEVER use `students.assigned_counsellor_l3_id`, it is sparsely populated.
- **"Supervisor" / "Team Owner" → `role ILIKE '%to%'`** — covers both `to` (L2 team owners) and `to_l3` (L3 team owners). NEVER use `role = 'to'` alone — it misses `to_l3` team owners.
- Team of a manager → `WHERE assigned_to = '<manager_counsellor_id>'`
- NEVER OR across two counsellor FK columns in one JOIN (Rule J1).

### Counsellor role meanings (Regular LMS):
| Role | Meaning |
|------|--------|
| `l2` | L2 counsellor — owns pre-application stages |
| `l3` | L3 counsellor — owns application/admission stages |
| `to` | Team Owner for L2 teams |
| `to_l3` | Team Owner for L3 teams |

### L2 vs L3 ownership (Regular LMS):
- **For counsellor-wise data or counsellor data queries, always show only L2 data unless L3 is explicitly requested.** When L3 is explicitly asked for, show only L3 data. Never mix L2 and L3 in the same output unless specifically requested.
- **L2 counsellor** (`assigned_counsellor_id` on `students`) owns the student from **Pre Application** through all pre-application stages** ( Pre Application → Initial Counselling Completed → Application → NotInterested before application). All these stages live in the `students` table.
- **L3 counsellor** (`assigned_counsellor_l3_id` on `students`) takes over from **Application stage through Admission and beyond** (Form Submitted → Exam/Interview → Offer Letter → Admission → Document Pending → Document Submitted → Enrolled → NotInterested after application). All these stages live in `course_status_journeys`.
- **CRITICAL — Regular LMS counsellors are course-wise:** In the Regular LMS, the L3 counsellor assignment is **per course**, not per student. A single student can have a different L3 counsellor for each course they applied to. When querying L3 counsellor performance, always join via `course_status_journeys.counsellor_id` (which tracks who handled each course-level event) rather than relying solely on `students.assigned_counsellor_l3_id`. For L2, the assignment is at the student level (`students.assigned_counsellor_id`).

### Business rules:
- **Primary table for Application, Admission, Document Pending, Document Submitted, Enrolled, and NotInterested (after application) queries.** Use `course_status` column.
- **This table is owned by L3 counsellors.** For L3-level queries, ALWAYS join via `course_status_journeys.assigned_l3_counsellor_id` — this is the correct column for identifying which L3 counsellor owns each course row. Do NOT use `students.assigned_counsellor_l3_id` for L3 lead counts — it is sparsely populated. `counsellor_id` on this table is who *logged* the event, not who is assigned.
- When user asks "form filled" / "form fills" / "applied" / "walkin" / "exam scheduled" / "offer letter" / "ready for admission" → query `course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Walkin Marked', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission')` from this table. These are the application-stage statuses for the Regular LMS.
- When user asks "admitted" / "got admission" / "admission" / "admissions" → query `course_status IN ('Admission', 'Enrolled')` from this table. **ALWAYS exclude partial payments from Admission status:** add `AND (fee_type NOT IN ('Partial Done', 'Partial Paid', 'Partially Paid') OR fee_type IS NULL)`. These are partial payment records, not complete admissions. **IMPORTANT:** Admission queries include BOTH Admission and Enrolled statuses because enrolled students have already been admitted.
- When user asks "document pending" / "docs pending" → query `course_status = 'Document Pending'` from this table.
- When user asks "document submitted" / "docs submitted" → query `course_status = 'Document Submitted'` from this table.
- When user asks "enrolled" → query `course_status = 'Enrolled'` from this table.
- NotInterested after application → `course_status = 'NotInterested'` from this table.
- No "Shortlisted" status exists in this table — for shortlisted queries use `latest_course_status = 'Shortlisted'` on `latest_course_statuses`.
- Latest status per student-course: `DISTINCT ON (student_id, course_id) ORDER BY student_id, course_id, created_at DESC` — gets the most recent status change for each student-course pair.
- First occurrence per student-course: `DISTINCT ON (student_id, course_id) ORDER BY student_id, course_id, created_at ASC` — gets the earliest status change for each student-course pair (e.g., first admission date).
- First occurrence of each status per student-course: `DISTINCT ON (student_id, course_id) ORDER BY student_id, course_id created_at ASC` — gets when each student first reached each specific status (see PATTERN 17).
- Total fees collected: `SUM(deposit_amount) WHERE deposit_amount > 0`.
- **All date-bounded stage counts (forms, admissions, enrolled, document pending/submitted):** For ANY query counting students in a date window from this table, ALWAYS use `MIN(created_at)` per `(student_id, course_id)` for the target status. A student-course pair is counted ONLY if it was their **first time** reaching that stage for that course within the window. Students who had already reached that stage before the window are excluded. See RULE CSJ-FORM.
- Use `MIN(created_at)` per `(student_id, course_id)` to deduplicate each student-course pair to their first application, admission or enrollment event, then apply the date filter on that deduplicated timestamp.

### MANDATORY FILTERS for course_status_journeys:

**RULE CSJ1 — Always validate student existence:**
When querying `course_status_journeys`, ALWAYS add:
`AND student_id IN (SELECT student_id FROM students)`

This filters out orphaned/test records that were deleted from `students` but remain in `course_status_journeys`.

**RULE CSJ2 — Always exclude partial payments from admission counts:**
When querying `course_status = 'Admission'`, ALWAYS add:
`AND (fee_type NOT IN ('Partial Done', 'Partial Paid', 'Partially Paid') OR fee_type IS NULL)`

These are partial payment records, not complete admissions.

**RULE CSJ3 — Use COUNT(DISTINCT student_id), never COUNT(*):**
When counting from `course_status_journeys`, ALWAYS use `COUNT(DISTINCT student_id)`.
NEVER use `COUNT(*)` as it counts rows, not unique students. The table is append-only with duplicate rows for the same student-course-status combination.

**RULE CSJ4 — Admission Grouping by Time Period:**
When counting admissions by time period (monthly, weekly, daily), ALWAYS use subquery with `MIN(created_at)` per `student_id` ONLY (not per student_id + course_id).
A student admitted to multiple courses in the same period should count as ONE admission.

Correct pattern:
```sql
WITH first_admission AS (
    SELECT student_id, MIN(created_at) AS first_admission_date
    FROM course_status_journeys
    WHERE course_status = 'Admission'
      AND (fee_type NOT IN ('Partial Done', 'Partial Paid', 'Partially Paid') OR fee_type IS NULL)
      AND student_id IN (SELECT student_id FROM students)
    GROUP BY student_id  -- ← ONLY student_id, NOT (student_id, course_id)
)
SELECT
    DATE_TRUNC('month', first_admission_date AT TIME ZONE 'Asia/Kolkata') AS month,
    COUNT(DISTINCT student_id) AS admissions
FROM first_admission
GROUP BY month
ORDER BY month;
```

**WRONG pattern (DO NOT USE):**
```sql
-- WRONG: Groups by both student_id AND course_id, causing overcounting
WITH first_admission AS (
    SELECT student_id, course_id, MIN(created_at) AS first_admission_date
    FROM course_status_journeys
    WHERE course_status = 'Admission'
    GROUP BY student_id, course_id  -- ← WRONG: will count same student multiple times
)
```
**RULE CSJ5 — Never include NULL values in fee_type filters:**
NEVER use `fee_type IS NULL` or add `OR fee_type IS NULL` in any fee_type filter. The database is not clean. Always use `fee_type NOT IN (...)` without the NULL clause to exclude dirty NULL records.

**RULE CSJ-FORM — ALL date-bounded stage counts use first-ever event per student-course:**
For ANY date-bounded count from `course_status_journeys` — forms, admissions, document pending, document submitted, enrolled, or any other stage — ALWAYS use `MIN(created_at)` per `(student_id, course_id)` for that status. A student-course pair is counted in the window ONLY if that was the **first time** they ever reached that stage for that course. Students who had already reached that stage before the window are excluded — regardless of re-triggers or additional rows.

This applies to:
- **Form fills** → `MIN(created_at)` per `(student_id, course_id)` across all application-stage statuses
- **Admissions yesterday/today** → `MIN(created_at)` per `(student_id, course_id)` where `course_status IN ('Admission', 'Enrolled')`
- **Document Pending yesterday/today** → `MIN(created_at)` per `(student_id, course_id)` where `course_status = 'Document Pending'`
- **Document Submitted yesterday/today** → `MIN(created_at)` per `(student_id, course_id)` where `course_status = 'Document Submitted'`
- **Enrolled yesterday/today** → `MIN(created_at)` per `(student_id, course_id)` where `course_status = 'Enrolled'`

**CORRECT pattern (applies to any stage — replace status filter as needed):**
```sql
WITH first_event AS (
    SELECT student_id, course_id, MIN(created_at) AS first_event_date
    FROM course_status_journeys
    WHERE course_status IN (<target statuses>)
    AND student_id IN (SELECT student_id FROM students)
    GROUP BY student_id, course_id
)
SELECT COUNT(DISTINCT fe.student_id)
FROM first_event fe
JOIN university_courses uc ON fe.course_id = uc.course_id
WHERE uc.university_name ILIKE '%University Name%'
  AND fe.first_event_date >= <start_ist>
  AND fe.first_event_date <  <end_ist>;
```

**WRONG pattern (DO NOT USE for any stage):**
```sql
-- WRONG: counts all rows in window, not first-ever event per student-course
SELECT COUNT(DISTINCT student_id)
FROM course_status_journeys
WHERE course_status IN (...)
  AND created_at >= <start_ist> AND created_at < <end_ist>;

**RULE CSJ-GROUPING — Ensure count consistency across different grouping dimensions:**
When writing queries that group by different dimensions (e.g., by university only vs by university + campaign), the total counts must always match. To ensure consistency:
1. **Identical WHERE clauses:** All variations of a query must have identical WHERE clause conditions, including NULL handling.
2. **Handle LEFT JOIN row multiplication:** When joining one-to-many tables (e.g., `student_lead_activities`), use subqueries to get a single value per student before joining to prevent the same student from being counted in multiple groups.

-- Get single campaign per student before joining

## OUTPUT FORMATTING RULES

- **MANDATORY — Percentage columns must always include the `%` symbol.** Whenever a query computes a percentage (connection rate, conversion rate, success rate, NI rate, form-to-admission rate, etc.), the column must concatenate the `%` symbol:
  ```sql
  ROUND(..., 2) || '%' AS connection_percentage
  ```
  NEVER return a bare numeric value for a percentage column. The `%` symbol must always be appended.

### PATTERN 2 — Stage breakdown per entity (wide/pivot format)

One row per entity, one column per stage. NEVER long format.
Early stages from `students`, later stages from `course_status_journeys`.

```sql
SELECT
    c.counsellor_name,
    COUNT(DISTINCT s.student_id) AS total_students,
    COUNT(DISTINCT CASE WHEN s.current_student_status = 'Pre Application' THEN s.student_id END) AS pre_application,
    COUNT(DISTINCT CASE WHEN csj.course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Walkin Marked', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission') THEN csj.student_id END) AS applications,
    COUNT(DISTINCT CASE WHEN csj.course_status = 'Admission' THEN csj.student_id END) AS admissions,
    COUNT(DISTINCT CASE WHEN csj.course_status = 'Document Pending' THEN csj.student_id END) AS document_pending,
    COUNT(DISTINCT CASE WHEN csj.course_status = 'Document Submitted' THEN csj.student_id END) AS document_submitted,
    COUNT(DISTINCT CASE WHEN csj.course_status = 'Enrolled' THEN csj.student_id END) AS enrolled
FROM counsellors c
JOIN students s ON c.counsellor_id = s.assigned_counsellor_id
LEFT JOIN course_status_journeys csj ON s.student_id = csj.student_id
GROUP BY c.counsellor_id, c.counsellor_name
ORDER BY total_students DESC;
```

### PATTERN 3 — Counsellor call performance (LEFT JOIN always)

```sql
SELECT
    c.counsellor_name,
    COUNT(sr.remark_id) AS total_calls,
    COUNT(CASE WHEN sr.calling_status = 'Connected' THEN 1 END) AS connected_calls,
    ROUND(
        COUNT(CASE WHEN sr.calling_status = 'Connected' THEN 1 END) * 100.0 /
        NULLIF(COUNT(sr.remark_id), 0), 2
    ) AS success_rate
FROM counsellors c
LEFT JOIN student_remarks sr ON c.counsellor_id = sr.counsellor_id
GROUP BY c.counsellor_id, c.counsellor_name
HAVING COUNT(sr.remark_id) > 0
ORDER BY success_rate DESC;
```

### PATTERN 4 — Team call performance

Team queries ALWAYS require: `manager → team_member (counsellors self-join) → student_remarks`. NEVER join students table for call metrics. ALWAYS include `WHERE manager.role ILIKE '%to%'` to cover both `to` (L2 team owners) and `to_l3` (L3 team owners).

```sql
SELECT
    manager.counsellor_name AS team_owner,
    COUNT(sr.remark_id) AS total_calls,
    COUNT(CASE WHEN sr.calling_status = 'Connected' THEN 1 END) AS connected_calls,
    ROUND(
        COUNT(CASE WHEN sr.calling_status = 'Connected' THEN 1 END) * 100.0 /
        NULLIF(COUNT(sr.remark_id), 0), 2
    ) AS success_rate
FROM counsellors manager
LEFT JOIN counsellors team_member ON manager.counsellor_id = team_member.assigned_to
LEFT JOIN student_remarks sr ON team_member.counsellor_id = sr.counsellor_id
WHERE manager.role ILIKE '%to%'    -- ← covers both 'to' (L2 team owners) and 'to_l3' (L3 team owners)
GROUP BY manager.counsellor_id, manager.counsellor_name
ORDER BY success_rate DESC;
```

**For distribution across teams (per team member breakdown):** GROUP BY both manager AND team_member:

SELECT
    manager.counsellor_name AS team_owner,

### PATTERN 5 — Benchmark / above-average comparison

```sql
WITH metrics AS (
    SELECT
        c.counsellor_id, c.counsellor_name,
        COUNT(sr.remark_id) AS total_calls,
        ROUND(COUNT(CASE WHEN sr.calling_status = 'Connected' THEN 1 END) * 100.0 /
              NULLIF(COUNT(sr.remark_id), 0), 2) AS success_rate
    FROM counsellors c
    LEFT JOIN student_remarks sr ON c.counsellor_id = sr.counsellor_id
    GROUP BY c.counsellor_id, c.counsellor_name
    HAVING COUNT(sr.remark_id) > 0
),
benchmark AS (
    SELECT AVG(success_rate) AS avg_rate, STDDEV(success_rate) AS stddev_rate FROM metrics
)
SELECT
    m.*, b.avg_rate AS benchmark_avg,
    CASE WHEN m.success_rate > b.avg_rate THEN 'Above Average'
         WHEN m.success_rate < b.avg_rate THEN 'Below Average'
         ELSE 'Average' END AS category
FROM metrics m CROSS JOIN benchmark b
ORDER BY m.success_rate DESC;
```

### PATTERN 7 — University deduplication (student at highest stage)

When a student has multiple courses at the same university, assign their highest stage using `course_status_journeys`:

```sql
WITH stage_priority AS (
    SELECT
        uc.university_name, csj.student_id,
        CASE
            WHEN csj.course_status = 'Enrolled'           THEN 6
            WHEN csj.course_status = 'Document Submitted' THEN 5
            WHEN csj.course_status = 'Document Pending'   THEN 4
            WHEN csj.course_status = 'Admission'          THEN 3
            WHEN csj.course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Walkin Marked', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission') THEN 2
            ELSE 0
        END AS stage_rank
    FROM university_courses uc
    JOIN course_status_journeys csj ON uc.course_id = csj.course_id
),
final_stage AS (
    SELECT university_name, student_id, MAX(stage_rank) AS final_rank
    FROM stage_priority GROUP BY university_name, student_id
)
SELECT
    university_name,
    COUNT(*) FILTER (WHERE final_rank = 2) AS applications,
    COUNT(*) FILTER (WHERE final_rank = 3) AS admissions,
    COUNT(*) FILTER (WHERE final_rank = 4) AS document_pending,
    COUNT(*) FILTER (WHERE final_rank = 5) AS document_submitted,
    COUNT(*) FILTER (WHERE final_rank = 6) AS enrolled
FROM final_stage
GROUP BY university_name ORDER BY admissions DESC;
```

### PATTERN 8 — Date-filtered count from course_status_journeys (ANY status)

Use this for ALL queries like for "for all admission/enrolled/application/document_pending/document_submitted" related queries like "admitted in last N days", "enrolled this month", "applications this week", etc.
Always wrap in a subquery with `MIN(created_at)` per student to get their first event date, then apply the IST-adjusted date filter.

```sql
SELECT COUNT(DISTINCT student_id) AS count
FROM (
    SELECT student_id, MIN(created_at) AS first_event_date
    FROM course_status_journeys
    WHERE course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Walkin Marked', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission')
      AND student_id IN (SELECT student_id FROM students)
    GROUP BY student_id
) sub
WHERE first_event_date >= CURRENT_DATE - interval 'N days' - interval '5 hours 30 minutes'
  AND first_event_date <  CURRENT_DATE + interval '1 day'  - interval '5 hours 30 minutes';
```

**Applies to all statuses:** application-stage IN list (Form Submitted – Portal Pending / Completed, Walkin Completed, Walkin Marked, Exam/Interview Scheduled, Offer Letter/Results Pending/Released), `'Admission'`, `'Document Pending'`, `'Document Submitted'`, `'Enrolled'`, `'NotInterested'` (after application).
**Why MIN?** `course_status_journeys` is append-only — a student can have multiple rows for the same `course_status` (re-triggers, duplicates). Without MIN, duplicates inflate counts and old students reappear in recent-period filters.

**⚠️ CRITICAL — NEVER do this (direct `created_at` filter on raw rows):**
```sql
-- WRONG — a student admitted in February whose row was re-triggered in March
-- will be counted as a March admission. This produces incorrect results.
SELECT COUNT(DISTINCT student_id)
FROM course_status_journeys
WHERE course_status = 'Admission'
  AND created_at >= '2026-03-01' AND created_at < '2026-04-01';

### PATTERN 9 — Conversion rate from application to admission

### PATTERN 11 — First Connected (total count + counsellor wise)

Counts students whose **very first Connected call** falls within a given date window. Uses `MIN(created_at)` to find each student's first connected event.
Apply the standard IST date window (see TIMEZONE RULES) for today / yesterday / last N days.

**Total first connected (any date window):**
```sql
WITH first_connected_dates AS (
  SELECT 
    student_id,
    MIN(created_at) AS first_connected_at
  FROM student_remarks
  WHERE calling_status = 'Connected'
    AND student_id IN (SELECT student_id FROM students)
  GROUP BY student_id
)
SELECT COUNT(DISTINCT fcd.student_id) AS first_connected_count
FROM first_connected_dates fcd
WHERE fcd.first_connected_at >= <start_ist>   -- e.g. CURRENT_DATE - INTERVAL '1 day' - INTERVAL '5 hours 30 minutes'
  AND fcd.first_connected_at <  <end_ist>;    -- e.g. CURRENT_DATE - INTERVAL '5 hours 30 minutes'
```

**First connected counsellor wise (any date window):**
```sql
SELECT
    c.counsellor_name,
    COUNT(DISTINCT sr.student_id) AS first_connected_count
FROM student_remarks sr
JOIN counsellors c 
    ON c.counsellor_id = sr.counsellor_id
WHERE sr.calling_status = 'Connected'
  AND sr.student_id IN (SELECT student_id FROM students)
  AND sr.created_at = (
        SELECT MIN(sr2.created_at)
        FROM student_remarks sr2
        WHERE sr2.student_id = sr.student_id
          AND sr2.calling_status = 'Connected'
  )
  AND sr.created_at >= <start_ist>   -- e.g. CURRENT_DATE - INTERVAL '1 day' - INTERVAL '5 hours 30 minutes'
  AND sr.created_at <  <end_ist>     -- e.g. CURRENT_DATE - INTERVAL '5 hours 30 minutes'
GROUP BY c.counsellor_id, c.counsellor_name
ORDER BY first_connected_count DESC;
```

**Key rule:** Always use `MIN(created_at)` (CTE or correlated subquery) to identify the first connected call. NEVER count all connected calls — that inflates the count for students connected multiple times.

**RULE J3 exception:** RULE J3 (`FROM counsellors LEFT JOIN student_remarks`) applies to full-roster call-metric queries. In the counsellor-wise variant above, the query drives FROM `student_remarks` → INNER JOIN `counsellors` intentionally — we only want counsellors who made a first-connected call. Do NOT flip this to `FROM counsellors LEFT JOIN student_remarks` here.

### PATTERN 12 — Pre-NI Students (date-filtered)

Counts students who went NI without ever having an ICC or progressing to application stage. Apply the standard IST date window (see TIMEZONE RULES) to `students.created_at` for today / yesterday / last N days.
**Pre-NI students added in a given date window:**
```sql
WITH never_progressed AS (
    SELECT s.student_id
    FROM students s
    WHERE s.current_student_status = 'NotInterested'
      AND s.first_icc_date IS NULL
      AND s.student_id NOT IN (
          SELECT DISTINCT student_id
          FROM course_status_journeys
          WHERE course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Walkin Marked', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission', 'Admission', 'Document Pending', 'Document Submitted', 'Enrolled')
      )
)
SELECT COUNT(DISTINCT np.student_id) AS pre_ni_count
FROM never_progressed np
JOIN students s ON np.student_id = s.student_id
WHERE s.created_at >= <start_ist>   -- e.g. CURRENT_DATE - INTERVAL '1 day' - INTERVAL '5 hours 30 minutes'
  AND s.created_at <  <end_ist>;    -- e.g. CURRENT_DATE - INTERVAL '5 hours 30 minutes'
```

**Definition of Pre-NI:** `current_student_status = 'NotInterested'` AND `first_icc_date IS NULL` AND student never appeared in `course_status_journeys` with a forward-progression status.

**Pre-NI counsellor wise (any date window):**
```sql
SELECT
    c.counsellor_name,
    COUNT(DISTINCT s.student_id) AS pre_ni_count
FROM students s
JOIN counsellors c ON s.assigned_counsellor_id = c.counsellor_id
WHERE s.current_student_status = 'NotInterested'
  AND s.first_icc_date IS NULL
  AND s.student_id NOT IN (
      SELECT DISTINCT student_id
      FROM course_status_journeys
      WHERE course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Walkin Marked', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission', 'Admission', 'Document Pending', 'Document Submitted', 'Enrolled')
  )
  AND s.created_at >= <start_ist>
  AND s.created_at <  <end_ist>
GROUP BY c.counsellor_id, c.counsellor_name
ORDER BY pre_ni_count DESC;

**Definition of Pre-NI:** `current_student_status = 'NotInterested'` AND `first_icc_date IS NULL` AND student never appeared in `course_status_journeys` with a forward-progression status.

**RULE F6 exception:** This is NOT a full-roster query. `JOIN counsellors` (INNER) is intentional — counsellors with zero pre-NI students are excluded by design. If the user explicitly asks for all counsellors, switch to `LEFT JOIN counsellors`.

### PATTERN 16 — First-Time Date Range: Per-Status Breakdown by University (or any entity)

**Use when the user asks for a breakdown by individual status** (e.g. "how many are Portal Pending vs Completed today", "status breakdown today by university"). This pattern deduplicates per individual status.

**DO NOT use this pattern for aggregate form-fill counts** (e.g. "how many forms yesterday", "how many applied today"). For aggregate form-fill counts, use PATTERN 17's `first_form` CTE with `MIN(created_at)` per `(student_id, course_id)` — see RULE CSJ-FORM.

**Why this pattern is needed for per-status breakdowns:**
`course_status_journeys` is append-only. Same student can have **two rows**. Filtering raw `created_at` on both rows would count the student in both columns simultaneously, inflating the "Portal Pending" count with students who have already moved forward. This pattern uses `DISTINCT ON (student_id, course_id, course_status) ORDER BY ... ASC` to capture the **first time** a student ever reached each individual status, then applies the date filter on that first-occurrence timestamp.

**Rule:** NEVER filter directly on raw `course_status_journeys.created_at` when counting per-status breakdowns for a date window. Always pick the earliest event per (student_id, course_id, course_status) first.

```sql
SELECT
    uc.university_name,
    COUNT(DISTINCT CASE WHEN fs.course_status = 'Form Submitted – Portal Pending' THEN fs.student_id END) AS form_submitted_portal_pending,
    COUNT(DISTINCT CASE WHEN fs.course_status = 'Form Submitted – Completed'      THEN fs.student_id END) AS form_submitted_completed
FROM (
    SELECT DISTINCT ON (student_id, course_id, course_status)
        student_id, course_id, course_status, assigned_l3_counsellor_id, created_at
    FROM course_status_journeys
    WHERE course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed')
      AND student_id IN (SELECT student_id FROM students)
    ORDER BY student_id, course_id, course_status, created_at ASC
) fs
JOIN university_courses uc ON fs.course_id = uc.course_id
WHERE uc.university_name IN ('University A', 'University B')
  AND fs.created_at >= CURRENT_DATE - INTERVAL '5 hours 30 minutes'
  AND fs.created_at <  CURRENT_DATE + INTERVAL '1 day' - INTERVAL '5 hours 30 minutes'
GROUP BY uc.university_name;
```

**Key rules:**
- `DISTINCT ON (student_id, course_id, course_status) ORDER BY ... created_at ASC` → picks the **first time** each student reached each status.
- The date filter goes on the outer query (on the already-deduplicated `fs.created_at`), not inside the subquery.
- Replace the `university_name IN (...)` filter and `GROUP BY` as needed — this pattern works for any grouping entity.
- Always include `AND student_id IN (SELECT student_id FROM students)` inside the subquery to exclude orphaned test records.
- **ALWAYS include any columns needed for outer JOINs in the `DISTINCT ON` subquery SELECT list.** For example, if joining counsellors on `assigned_l3_counsellor_id`, include it in the subquery SELECT. Columns not selected inside the subquery cannot be referenced outside it.

### PATTERN 17 — Forms and Admissions by University (Monthly/Custom Date Range)

Use when user asks for forms and admissions counts for specific universities over a date range (monthly, till date, today, yesterday, custom period). This pattern uses CTEs to deduplicate both forms and admissions, then counts them separately with UNION ALL.

**Definition of "form filled yesterday/today/this week":** A student-course pair is counted in the date window only if it was the **first time** that student ever applied to that course (`MIN(created_at)` per `student_id, course_id`). Students who had previously applied to the same course before the window are excluded. This matches RULE CSJ-FORM.

**Key features:**
- Deduplicates forms per `(student_id, course_id)` using `MIN(created_at)` — first-ever form per student-course
- Deduplicates admissions per `(student_id, course_id)` using `MIN(created_at)`
- **Does NOT exclude any fee_type values** - counts all admissions regardless of payment status
- Validates student existence
- Flexible date range (can be adapted for monthly, today, yesterday, till date, etc.)
- Works for any university

**Template:**
```sql
-- ================= FORMS =================
WITH first_form AS (
    SELECT 
        student_id,
        course_id,
        assigned_l3_counsellor_id,
        MIN(created_at) AS first_form_date
    FROM course_status_journeys
    WHERE course_status IN (
        'Form Submitted – Portal Pending', 
        'Form Submitted – Completed', 
        'Walkin Completed', 
        'Walkin Marked',
        'Exam/Interview Scheduled',
        'Offer Letter/Results Pending',
        'Offer Letter/Results Released',
        'Ready For Admission'
    )
    AND student_id IN (SELECT student_id FROM students)
    GROUP BY student_id, course_id, assigned_l3_counsellor_id
),
-- Deduplicate to one row per student (earliest form event) for counsellor-wise counting
deduped_forms AS (
    SELECT DISTINCT ON (student_id)
        student_id,
        assigned_l3_counsellor_id,
        first_form_date
    FROM first_form
    ORDER BY student_id, first_form_date ASC
),

-- ================= ADMISSIONS =================
first_admission AS (
    SELECT 
        student_id,
        course_id,
        MIN(created_at) AS first_admission_date
    FROM course_status_journeys
    WHERE course_status = 'Admission'
      AND (fee_type NOT IN ('Partial Done', 'Partial Paid', 'Partially Paid'))
    GROUP BY student_id, course_id
)

SELECT 
    'Forms' AS metric,
    COUNT(*) AS total_count
FROM first_form ff
INNER JOIN university_courses uc 
    ON ff.course_id = uc.course_id
WHERE 
    uc.university_name ILIKE '<University Name>'
    AND ff.first_form_date >= '<start_date>'::timestamptz - INTERVAL '5 hours 30 minutes'
    AND ff.first_form_date <  '<end_date>'::timestamptz - INTERVAL '5 hours 30 minutes'

UNION ALL

SELECT 
    'Admissions' AS metric,
    COUNT(*) AS total_count
FROM first_admission fa
INNER JOIN university_courses uc 
    ON fa.course_id = uc.course_id
WHERE 
    uc.university_name ILIKE '<University Name>'
    AND fa.first_admission_date >= '<start_date>'::timestamptz - INTERVAL '5 hours 30 minutes'
    AND fa.first_admission_date <  '<end_date>'::timestamptz - INTERVAL '5 hours 30 minutes'

ORDER BY metric;
```

**Adaptation examples:**

**Monthly (e.g., April 2026):**
```sql
-- Replace date filters with:
AND ff.first_form_date >= '2026-04-01 00:00:00'::timestamptz - INTERVAL '5 hours 30 minutes'
AND ff.first_form_date <  '2026-05-01 00:00:00'::timestamptz - INTERVAL '5 hours 30 minutes'
```

**Till date (from start of year to today):**
```sql
-- Replace date filters with:
AND ff.first_form_date >= '2026-01-01 00:00:00'::timestamptz - INTERVAL '5 hours 30 minutes'
AND ff.first_form_date <  CURRENT_DATE + INTERVAL '1 day' - INTERVAL '5 hours 30 minutes'
```

**Today only:**
```sql
-- Replace date filters with:
AND ff.first_form_date >= CURRENT_DATE - INTERVAL '5 hours 30 minutes'
AND ff.first_form_date <  CURRENT_DATE + INTERVAL '1 day' - INTERVAL '5 hours 30 minutes'
```

**Yesterday:**
```sql
-- Replace date filters with:
AND ff.first_form_date >= CURRENT_DATE - INTERVAL '1 day' - INTERVAL '5 hours 30 minutes'
AND ff.first_form_date <  CURRENT_DATE - INTERVAL '5 hours 30 minutes'
```

**Custom date range (e.g., April 1-10, 2026):**
```sql
-- Replace date filters with:
AND ff.first_form_date >= '2026-04-01 00:00:00'::timestamptz - INTERVAL '5 hours 30 minutes'
AND ff.first_form_date <  '2026-04-11 00:00:00'::timestamptz - INTERVAL '5 hours 30 minutes'
```

**Multiple universities:**
```sql
-- Replace university filter with:
WHERE uc.university_name IN ('University A', 'University B', 'University C')
-- And add GROUP BY to see breakdown:
GROUP BY uc.university_name, metric
ORDER BY uc.university_name, metric;
```

**Key rules:**
- Forms are deduplicated per `(student_id, course_id)` because a student can apply to multiple courses
- Admissions are deduplicated per `(student_id, course_id)` for consistency with forms
- Use `COUNT(DISTINCT student_id)` in final SELECT to count unique students
- Always use `ILIKE` for university name matching (case-insensitive, handles spelling variations)
- **This pattern does NOT exclude partial payments** - it counts all admissions regardless of fee_type
- Always validate student existence with `AND student_id IN (SELECT student_id FROM students)`
- Date filters use IST timezone offset (`- INTERVAL '5 hours 30 minutes'`)
- **Alternative deduplication method:** Instead of `MIN(created_at) GROUP BY student_id, course_id`, you can use `DISTINCT ON (student_id, course_id) ORDER BY student_id, course_id, created_at ASC` to get the first occurrence per student-course pair. Both methods work equally well.
- **CRITICAL:** `course_status_journeys` has multiple entries for the same student-course-status combination due to re-triggers and updates. ALWAYS deduplicate using either `MIN(created_at)` or `DISTINCT ON` before applying date filters or counting.
- **CRITICAL — counsellor-wise forms:** After `first_form` CTE, ALWAYS add a `deduped_forms` CTE using `DISTINCT ON (student_id) ORDER BY student_id, first_form_date ASC` before joining counsellors. Without this, a student who applied to N universities is counted N times under the same counsellor, inflating the total. NEVER drive the final SELECT directly from `first_form` for counsellor-wise counts.

### PATTERN 18 — L3 Form Assignment Performance and Response Time Breakdown

Use when user asks for L3 counsellor performance on form assignments, including: "L3 form metrics", "how many forms per L3", "L3 response time breakdown", "forms not initiated by L3", "L3 counsellor form TAT", "active vs completed forms per L3".

**Key features:**
- Shows total forms assigned to each L3 counsellor (per student-course combination)
- Breaks down active vs completed forms
- Identifies forms not yet initiated (no remark from assigned L3)
- Categorizes response time: within 3 days, 4-6 days, 7+ days
- Uses `assigned_l3_counsellor_id` from `course_status_journeys` (correct L3 ownership column)
- Deduplicates using `DISTINCT ON (student_id, course_id)` for first and latest status
- Only counts remarks made by the assigned L3 counsellor (not other counsellors)

**Business rules applied:**
- Excludes 'Shortlisted' status (not an active form submission)
- Active forms = latest status NOT IN ('Registration done', 'Partially Paid', 'Semester Paid', 'Enrollment in Process', 'Enrolled')
- Response time calculated from first status date to first remark by assigned L3 counsellor
- Uses `GREATEST(0, ...)` to handle cases where remark was made before status (counts as 0 days)
- Student-course combinations tracked via composite key to ensure accurate deduplication

**Template:**
```sql
WITH 
      -- ALL distinct student-course combinations
      all_combinations AS (
        SELECT DISTINCT 
            student_id, 
            course_id
        FROM course_status_journeys
        WHERE student_id IN (SELECT student_id FROM students)  -- Validate student existence
      ),

      -- Get first status details for each combination
      first_status AS (
        SELECT DISTINCT ON (student_id, course_id)
            student_id,
            course_id,
            course_status,
            created_at AS first_status_date,
            counsellor_id AS status_created_by,
            assigned_l3_counsellor_id  -- The L3 counsellor assigned to this student-course
        FROM course_status_journeys
        WHERE student_id IN (SELECT student_id FROM students)
        ORDER BY student_id, course_id, created_at ASC
      ),

      -- Get FIRST remark by the ASSIGNED L3 COUNSELLOR for each student-course
      first_remark_by_l3 AS (
        SELECT DISTINCT ON (fs.student_id, fs.course_id)
            fs.student_id,
            fs.course_id,
            sr.created_at AS first_remark_date
        FROM first_status fs
        LEFT JOIN student_remarks sr 
            ON sr.student_id = fs.student_id 
            AND sr.counsellor_id = fs.assigned_l3_counsellor_id  -- Only remarks by the assigned L3 counsellor
        WHERE sr.student_id IN (SELECT student_id FROM students)
        ORDER BY fs.student_id, fs.course_id, sr.created_at ASC
      ),

      -- Get latest status for active check
      latest_status AS (
        SELECT DISTINCT ON (student_id, course_id)
            student_id,
            course_id,
            course_status AS latest_status
        FROM course_status_journeys
        WHERE student_id IN (SELECT student_id FROM students)
        ORDER BY student_id, course_id, created_at DESC
      ),

      -- Base table with ALL combinations
      base AS (
        SELECT 
            ac.student_id,
            ac.course_id,
            fs.first_status_date,
            fs.status_created_by,
            fs.assigned_l3_counsellor_id,
            fr.first_remark_date,  -- First remark by assigned L3 counsellor (NULL if no remark)
            ls.latest_status,
            -- Calculate days difference ONLY if remark exists
            CASE 
                WHEN fr.first_remark_date IS NOT NULL 
                THEN GREATEST(0, EXTRACT(DAY FROM (fr.first_remark_date - fs.first_status_date)))
                ELSE NULL
            END AS days_to_first_action,
            c.counsellor_name,
            CONCAT(ac.student_id, '_', ac.course_id) AS student_course_key
        FROM all_combinations ac
        JOIN first_status fs ON ac.student_id = fs.student_id AND ac.course_id = fs.course_id
        LEFT JOIN first_remark_by_l3 fr ON ac.student_id = fr.student_id AND ac.course_id = fr.course_id
        LEFT JOIN latest_status ls ON ac.student_id = ls.student_id AND ac.course_id = ls.course_id
        LEFT JOIN counsellors c ON fs.assigned_l3_counsellor_id = c.counsellor_id
        WHERE fs.course_status <> 'Shortlisted'
      )

      SELECT 
          COALESCE(b.assigned_l3_counsellor_id, 'Unassigned') AS assigned_l3_counsellor_id,
          COALESCE(b.counsellor_name, 'Unassigned') AS counsellor_name,
          
          -- TOTAL FORMS: All combinations for this L3 counsellor
          COUNT(DISTINCT b.student_course_key) AS total_forms,
          
          -- ACTIVE FORMS: Where latest status is not completed
          COUNT(DISTINCT CASE 
              WHEN b.latest_status NOT IN (
                'Registration done',
                'Partially Paid',
                'Semester Paid',
                'Enrollment in Process',
                'Enrolled'
              ) OR b.latest_status IS NULL
              THEN b.student_course_key 
          END) AS active_forms,
          
          -- NOT INITIATED: NO remark from assigned L3 counsellor
          COUNT(DISTINCT CASE 
              WHEN b.first_remark_date IS NULL 
              THEN b.student_course_key 
          END) AS not_initiated_count,
          
          -- CALLED WITHIN 3 DAYS: First remark by L3 counsellor within 3 days (including before status)
          COUNT(DISTINCT CASE 
              WHEN b.first_remark_date IS NOT NULL 
              AND b.days_to_first_action BETWEEN 0 AND 3
              THEN b.student_course_key 
          END) AS called_within_3_days,
          
          -- CALLED 4-6 DAYS: First remark by L3 counsellor 4-6 days after status
          COUNT(DISTINCT CASE 
              WHEN b.first_remark_date IS NOT NULL 
              AND b.days_to_first_action BETWEEN 4 AND 6
              THEN b.student_course_key 
          END) AS called_4_to_6_days,
          
          -- CALLED 7+ DAYS: First remark by L3 counsellor 7+ days after status
          COUNT(DISTINCT CASE 
              WHEN b.first_remark_date IS NOT NULL 
              AND b.days_to_first_action >= 7
              THEN b.student_course_key 
          END) AS called_7_plus_days
          
      FROM base b
      GROUP BY b.assigned_l3_counsellor_id, b.counsellor_name
      ORDER BY total_forms DESC;
```

**Key rules:**
- **CRITICAL:** Uses `course_status_journeys.assigned_l3_counsellor_id` for L3 ownership (NOT `students.assigned_counsellor_l3_id`)
- **Deduplication:** `DISTINCT ON (student_id, course_id)` with `ORDER BY created_at ASC` for first status, `DESC` for latest status
- **Student-course key:** Uses `CONCAT(student_id, '_', course_id)` to ensure accurate counting of unique combinations
- **Response time logic:** Only calculates days if a remark exists; uses `GREATEST(0, ...)` to handle pre-status remarks
- **Remark filtering:** Only counts remarks where `sr.counsellor_id = fs.assigned_l3_counsellor_id` (remarks by the assigned L3, not other counsellors)
- **Active forms:** Excludes terminal statuses (Registration done, Partially Paid, Semester Paid, Enrollment in Process, Enrolled)
- **Student validation:** Applies `AND student_id IN (SELECT student_id FROM students)` in all CTEs to exclude orphaned records
- **Excludes Shortlisted:** Filters out `course_status = 'Shortlisted'` as it's not an active form submission

**Adaptation examples:**

**Add date filter (e.g., forms assigned in last 30 days):**
```sql

WHERE student_id IN (SELECT student_id FROM students)
  AND created_at >= CURRENT_DATE - INTERVAL '30 days' - INTERVAL '5 hours 30 minutes'
  AND created_at < CURRENT_DATE + INTERVAL '1 day' - INTERVAL '5 hours 30 minutes'
```

**Filter by specific L3 counsellor:**
```sql
-- Add to final SELECT:
WHERE b.assigned_l3_counsellor_id = 'CNS-XXXX'
```

**Include only active counsellors:**
```sql
-- Modify counsellors JOIN in base CTE:
LEFT JOIN counsellors c ON fs.assigned_l3_counsellor_id = c.counsellor_id
    AND c.status = 'active'
```

### PATTERN 19 — L3 TAT: Time from L3 Assignment to First Connected Call

Use when user asks: "avg TAT for L3", "how long does L3 take to connect", "average response time after L3 assignment", "time to first connected call after receiving lead from L2", "L3 TAT raw data", "L3 connected call stats".

**CRITICAL:** Always use `course_status_journeys.assigned_l3_counsellor_id` for L3 counsellor identification — NOT `students.assigned_counsellor_l3_id` (sparsely populated). Always use `MIN(created_at)` in subqueries to avoid row multiplication.

**Variant A — Raw data (one row per student, per L3 counsellor):**
Use when user asks for "raw data", "list", "show me the details", "individual TAT".
```sql
SELECT
    c.counsellor_name,
    first_assign.student_id,
    first_assign.first_assigned_at AT TIME ZONE 'Asia/Kolkata' AS assigned_at_ist,
    first_call.first_connected_at AT TIME ZONE 'Asia/Kolkata' AS first_connected_ist,
    ROUND(EXTRACT(EPOCH FROM (first_call.first_connected_at - first_assign.first_assigned_at)) / 3600, 2) AS tat_hours
FROM counsellors c
JOIN (
    SELECT assigned_l3_counsellor_id, student_id, MIN(created_at) AS first_assigned_at
    FROM course_status_journeys
    WHERE assigned_l3_counsellor_id IS NOT NULL
    GROUP BY assigned_l3_counsellor_id, student_id
) first_assign
    ON c.counsellor_id = first_assign.assigned_l3_counsellor_id
JOIN (
    SELECT sr.student_id, sr.counsellor_id, MIN(sr.created_at) AS first_connected_at
    FROM student_remarks sr
    WHERE sr.calling_status = 'Connected'
    GROUP BY sr.student_id, sr.counsellor_id
) first_call
    ON first_assign.student_id = first_call.student_id
    AND first_assign.assigned_l3_counsellor_id = first_call.counsellor_id
WHERE c.role = 'l3'
  AND c.status = 'active'
  AND first_call.first_connected_at >= first_assign.first_assigned_at
ORDER BY c.counsellor_name, tat_hours DESC;
```

**Variant B — Counsellor-wise average TAT:**
Use when user asks for "avg TAT per L3 counsellor", "which L3 is fastest", "average response time by counsellor".
```sql
SELECT
    c.counsellor_name,
    AVG(EXTRACT(EPOCH FROM (first_call.first_connected_at - first_assign.first_assigned_at)) / 3600) AS avg_tat_hours
FROM counsellors c
JOIN (
    SELECT assigned_l3_counsellor_id, student_id, MIN(created_at) AS first_assigned_at
    FROM course_status_journeys
    WHERE assigned_l3_counsellor_id IS NOT NULL
    GROUP BY assigned_l3_counsellor_id, student_id
) first_assign ON c.counsellor_id = first_assign.assigned_l3_counsellor_id
JOIN (
    SELECT student_id, MIN(created_at) AS first_connected_at
    FROM student_remarks
    WHERE calling_status = 'Connected'

### PATTERN 21 — NI Reason Breakdown by Campaign (Why Students Are Not Interested)

Use when the user asks: "why are students not interested", "NI reasons by campaign", "campaign wise NI analysis", "not interested breakdown by campaign", "which campaign has most NI", "NI sub-status by campaign".

**What it does:** For a given date window, shows each campaign's total leads, then breaks them down into NI sub-status reasons vs "Interested / In-Progress", with percentage of total. Uses `COALESCE(utm_campaign, 'Direct/Organic')` to bucket leads with no UTM as organic.

```sql
WITH fresh_leads AS (
    SELECT student_id
    FROM students
    WHERE created_at >= CURRENT_DATE - INTERVAL '5 hours 30 minutes'
      AND created_at < CURRENT_DATE + INTERVAL '1 day' - INTERVAL '5 hours 30 minutes'
),
campaign_totals AS (
    SELECT
        COALESCE(sla.utm_campaign, 'Direct/Organic') AS campaign,
        COUNT(DISTINCT fl.student_id) AS total_leads
    FROM fresh_leads fl
    LEFT JOIN student_lead_activities sla ON fl.student_id = sla.student_id
    GROUP BY 1
),
WITH fresh_leads AS (
    SELECT student_id
    FROM students
    WHERE created_at >= CURRENT_DATE - INTERVAL '5 hours 30 minutes'
      AND created_at < CURRENT_DATE + INTERVAL '1 day' - INTERVAL '5 hours 30 minutes'
),
campaign_totals AS (
    SELECT
        COALESCE(sla.utm_campaign, 'Direct/Organic') AS campaign,
        COUNT(DISTINCT fl.student_id) AS total_leads
    FROM fresh_leads fl
    LEFT JOIN student_lead_activities sla ON fl.student_id = sla.student_id
    GROUP BY 1
),
status_breakdown AS (
    SELECT
        COALESCE(sla.utm_campaign, 'Direct/Organic') AS campaign,
        COALESCE(s.current_student_ni_sub_status, 'Reason Not Given') AS not_interested_reason,
        COUNT(DISTINCT fl.student_id) AS ni_count
    FROM fresh_leads fl
    JOIN students s ON fl.student_id = s.student_id
    LEFT JOIN student_lead_activities sla ON fl.student_id = sla.student_id
    WHERE s.current_student_status = 'NotInterested'
    GROUP BY 1, 2
)
SELECT
    ct.campaign,
    ct.total_leads,
    sb.not_interested_reason,
    sb.ni_count,
    ROUND((sb.ni_count::numeric * 100.0 / ct.total_leads), 2) AS percentage_of_total
FROM campaign_totals ct
JOIN status_breakdown sb ON ct.campaign = sb.campaign
ORDER BY ct.total_leads DESC, sb.ni_count DESC;
SELECT
    ct.campaign,
    ct.total_leads,
    sb.not_interested_reason,
    sb.ni_count,
    ROUND((sb.ni_count::numeric * 100.0 / ct.total_leads), 2) AS percentage_of_total
FROM campaign_totals ct
JOIN status_breakdown sb ON ct.campaign = sb.campaign
ORDER BY ct.total_leads DESC, sb.ni_count DESC;
```

**Key rules:**
- When current_student_ni_sub_status is null use only ELSE 'Reason Not Given'. Do not this when it is null ELSE 'Interested / In-Progress' this will create ambigous result.
- `COALESCE(sla.utm_campaign, 'Direct/Organic')` — leads with no UTM activity row or NULL campaign are grouped as `'Direct/Organic'`.
- `LEFT JOIN student_lead_activities` — use LEFT JOIN so students with no activity row are still counted (they fall into `'Direct/Organic'`).
- `lead_segment` = `current_student_ni_sub_status` for NI students, `'Reason not given'` for all others. Do NOT filter by `current_student_status = 'NotInterested'` inside the CTE — all statuses must be included for the total to be accurate.
- Date window applies to `students.created_at` (IST-adjusted). Adjust the window using standard IST offset when the user specifies a different period.
- `percentage_of_total` = `segment_count / total_leads * 100`, rounded to 2 decimal places.
- `COUNT(DISTINCT s.student_id)` in both CTEs — never `COUNT(*)`.

### FILTER RULES

**RULE F1.** NEVER add `counsellors.status = 'active'` unless user explicitly says "active counsellors".

**RULE F2.** NEVER add `is_partner` filter unless user mentions "internal", "partner", or "external".

**RULE F3.** NEVER add LIMIT unless:
- User says "top N" or gives an explicit count, OR
- User uses a superlative ("which has the most / least / best / worst / highest / lowest") → then add `LIMIT 1`.

**RULE F7.** When the user asks for counsellors who make "many calls" but have "low success", use hardcoded thresholds: `HAVING COUNT(*) >= 10 AND (connected/total * 100) < 30`. Do NOT use dynamic averages — the question implies absolute thresholds, not relative ones.

**RULE F4.** NEVER filter by `current_student_status` on a "total lead count over time" query.

**RULE F5.** NEVER add a status WHERE clause on a full-funnel query. Use UNION ALL or CASE WHEN.

**RULE F6.** NEVER add HAVING clauses unless the user asks to filter by a minimum count or threshold. A full-roster report ("each counsellor", "all counsellors") must include zero-call counsellors — do not filter them out with HAVING. HAVING is only valid for: superlative + LIMIT 1 queries, or explicit outlier filters like Easy_37.

**RULE F8.** NEVER add WHERE filters that were not asked for. Specifically:
- NEVER add `WHERE manager.role = 'to'` when the query identifies a team by manager name (ILIKE '%Name%'). The name filter alone is sufficient — adding a role guard will silently return zero rows if the role value differs.
- NEVER add `WHERE c.role IN ('l2','l3')` or any role filter on counsellor queries unless the user explicitly specifies a role.
- `WHERE manager.role ILIKE '%to%'` is ONLY valid for ALL-teams queries (no specific manager named). This covers both `to` (L2 team owners) and `to_l3` (L3 team owners).

**RULE F9.** **University Name with Location Qualifier — Always use AND, never OR.**
When the user refers to a university by a name that includes a location (e.g. "Chandigarh University, Lucknow", "Chandigarh University Lucknow", "Amity University Noida"), the `university_name` column in `university_courses` stores the **full composite name** including the city/campus. You MUST match both the university name and the location using `AND`:
- **CORRECT:** `uc.university_name ILIKE '%Chandigarh University%' AND uc.university_name ILIKE '%Lucknow%'`
- **WRONG:** `uc.university_name ILIKE '%Chandigarh University%' OR uc.university_name ILIKE '%Lucknow%'`

**Why this matters:** Using `OR` will match:
1. Every campus of "Chandigarh University" (e.g. Chandigarh University Punjab, Chandigarh University Mohali) — not just Lucknow, AND
2. Any unrelated university that happens to contain "Lucknow" in its name.
This inflates results and produces an incorrect count. Using `AND` ensures only courses from the specific campus (university name containing BOTH terms) are matched.

**This rule applies everywhere** `university_name` is filtered: in WHERE clauses, CTEs, subqueries, and any pattern (PATTERN 11, 17, 18, etc.).

These two columns share similar values but are entirely different — they are not interchangeable.

**RULE T11.** Fee column selection — two entirely different concepts, NEVER interchangeable:
- "Total fee" / "admission fee" / "course fee" / "how much is the course" / "course worth" / "fee structure" → `university_courses.total_fees` (catalog price).
- "Deposit" / "deposit amount" / "amount paid" / "payment collected" / "fees received" → `course_status_journeys.deposit_amount` (actual payment made by student).
- `university_courses` also has `semester_fees` (per semester) and `annual_fees` (per year) — use these when the user asks specifically for per-semester or per-year fee breakdowns.

**RULE T12.** **Validation Check.** You **MUST** ensure every query filters for valid students. Test leads may have been deleted from `students` but their records persist in child tables (`student_remarks`, `course_status_journeys`, `latest_course_statuses`, `student_lead_activities`) as orphaned rows. These orphaned records must NEVER be counted or returned.
- When the child table is already JOINed to `students` (directly or via a chain), no extra filter is needed.
- If the `students` table is not explicitly JOINed, you **MUST** add: `WHERE student_id IN (SELECT student_id FROM students)`
- This applies to **every single query** using child tables — counts, lists, aggregations, subqueries, and CTEs. No exceptions.

### STATUS / COLUMN RULES

**RULE S1.** `students.current_student_status` is the source for early funnel stages (Pre Application, Initial Counselling Completed, NotInterested before application). For Application, Admission, Document Pending, Document Submitted, Enrolled, and NotInterested after application → use `course_status_journeys.course_status`.

**RULE S2.** When user asks "form filled" or "form fills" or "applied" → query `course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Walkin Marked', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission')` from `course_status_journeys`. NEVER use `latest_course_statuses` for this. NEVER use `course_status = 'Application'` in Regular LMS — that status does not exist.

**RULE S3.** Count callbacks using `remark_id`, not `student_id`.

**RULE S4.** NEVER use `students.remarks_count` for metrics. Always use `COUNT(DISTINCT sr.remark_id)` after joining `student_remarks`.

**RULE S12.** When asked about total ICC / total initial counselling calls / ICC count — in any form — ALWAYS use `first_icc_date` from `students`. Count as `COUNT(DISTINCT student_id) WHERE first_icc_date IS NOT NULL`. Do NOT use `current_student_status = 'Initial Counselling Completed'` for this metric.

**RULE S14.** Standard ICC count query — ALWAYS use this exact pattern for counting ICC:
```sql
SELECT COUNT(*) FROM students 
WHERE first_icc_date IS NOT NULL
```
This is the canonical way to count total ICC. Never use `COUNT(DISTINCT student_id)` for this specific query pattern unless joining other tables.

**RULE S16.** **The Admission Stage is Dirty Data.** Any time you reference `course_status = 'Admission'` (whether for a **COUNT**, a **SUM**, a **List/Display**, or a **Join**), you **MUST** immediately append: `AND fee_type NOT IN ('partial paid', 'Partially Paid', 'Partial Done')`. This is a global requirement for the Admission status. These rows represent partial fee events recorded under Admission status, not confirmed admissions.
- **Do NOT apply this exclusion to any other status.** Specifically, `'Enrolled'` is a clean status and does NOT need the `fee_type` filter.
- Exclude `'Registration done'` only when the user explicitly says "remove registration done", "exclude registration done", or similar. Do not exclude it by default.
- Example default admission filter: `WHERE course_status = 'Admission' AND fee_type NOT IN ('partial paid', 'Partially Paid', 'Partial Done')`
- Example with registration excluded: `WHERE course_status = 'Admission' AND fee_type NOT IN ('partial paid', 'Partially Paid', 'Partial Done', 'Registration done')`

**RULE S17.** **Admission Counts Must Be Deduplicated.** `course_status_journeys` is append-only — the same student can have multiple `course_status = 'Admission'` rows for the same course (re-triggers, updates, corrections). ALWAYS use `COUNT(DISTINCT student_id)` for admission counts. NEVER use `COUNT(*)` or `COUNT(remark_id)` on admission rows. For any query returning a list or detail of admitted students, wrap in a CTE using `MIN(created_at)` or `DISTINCT ON (student_id, course_id)` to ensure one row per student-course pair before joining or displaying results.
- Correct: `COUNT(DISTINCT student_id) WHERE course_status = 'Admission' AND fee_type NOT IN ('partial paid', 'Partially Paid', 'Partial Done')`
- Wrong: `COUNT(*) WHERE course_status = 'Admission'` — this inflates counts due to duplicate rows for the same student.

**RULE S18.** **course_status_journeys is Append-Only — Always Deduplicate Before Filtering by Date.** For ANY query that filters `course_status_journeys` by a date window to count or list students at a specific status, you MUST deduplicate first using one of these two approaches:
- **`MIN(created_at)` per `(student_id, course_id)`** — use when you only need one status (e.g. "admitted today", "enrolled this week"). Get the first event date, then apply the date filter outside. See PATTERN 11.
- **`DISTINCT ON (student_id, course_id, course_status) ORDER BY ... created_at ASC`** — use when you need multiple statuses in a pivot/breakdown (e.g. "portal pending vs completed today"). Get the first occurrence of each status per student, then apply the date filter outside. See PATTERN 17.

**Why:** The same student-course-status combination can have many rows due to re-triggers, corrections, and updates. Without deduplication, a student first admitted in February whose row was re-triggered in March will be counted as a March admission. A student who moved from Portal Pending → Completed will appear in both Portal Pending AND Completed columns.

**NEVER filter raw `course_status_journeys.created_at` directly** without first deduplicating. This is a global rule with no exceptions.

**RULE S15.** **TAT / Average Days Calculation.** For any query involving "average days," "how long," "time taken," or "TAT," it is **strictly forbidden** to join the raw `course_status_journeys` table directly. You **MUST** use a subquery or CTE with `MIN(created_at) GROUP BY student_id, course_id` to find the **first** time they reached that status before calculating the date difference. This prevents overcounting from status updates and re-triggers.

For date-filtered queries on `course_status_journeys` (Application, Admission, Document Pending, Document Submitted, Enrolled, NotInterested after application), use `MIN(created_at)` per student to get their first event date, then apply the date filter on that. This ensures accurate counts by avoiding duplicate rows for the same `course_status` (re-triggers, duplicates). Use PATTERN 11 — subquery with `MIN(created_at)` grouped by `student_id`, then filter on `first_event_date`.

**RULE S5.** ALWAYS use `COUNT(DISTINCT student_id)` when counting students — never `COUNT(*)` after a JOIN.


**RULE S6.** "Form filled" / "form fills" / "applied" → `course_status IN ('Form Submitted – Portal Pending', 'Form Submitted – Completed', 'Walkin Completed', 'Walkin Marked', 'Exam/Interview Scheduled', 'Offer Letter/Results Pending', 'Offer Letter/Results Released', 'Ready For Admission')` on `course_status_journeys`. Do NOT use `latest_course_statuses` for form fill queries. NEVER use `course_status = 'Application'` in Regular LMS.

**RULE S8.** For time-slot / hourly performance queries ("best time", "worst time", "perform best at what hour", "connected at 9 AM"):
- ALWAYS use `EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Kolkata')` on `student_remarks`.
- Performance = `calling_status = 'Connected'` rate only.
- Always include `HAVING COUNT(*) > 0`.
- Add `LIMIT 1` when asking for a single best/worst slot.

**RULE S9.** When a query must return BOTH a total count AND a filtered subset count for the same entity (e.g. total students AND admitted students per counsellor), use CASE WHEN inside COUNT. Using WHERE drops all non-matching rows, making the total count impossible.

Example: `COUNT(DISTINCT csj.student_id) AS total_students, COUNT(DISTINCT CASE WHEN csj.course_status = 'Admission' THEN csj.student_id END) AS admissions, COUNT(DISTINCT CASE WHEN csj.course_status = 'Document Pending' THEN csj.student_id END) AS document_pending`

**RULE S10.** "Spread across teams" / "distribution across teams" / "per team breakdown" means one row per team member (GROUP BY both manager AND team_member). It does NOT mean one aggregated row per team. If the question asks how something is distributed or spread, always include the member-level detail:
- Group by `manager.counsellor_id, manager.counsellor_name, team_member.counsellor_id, team_member.counsellor_name`

### JOIN RULES

**RULE J1.** When joining two counsellor FK columns, use two separate subqueries or determine L2 vs L3 from context. Use the following format:
```sql
ON c.counsellor_id = s.assigned_counsellor_id
```
or
```sql
ON c.counsellor_id = s.assigned_counsellor_l3_id
```
Do not combine these conditions with OR in a single JOIN.

**RULE J2.** NEVER filter by counsellor name on any base table. Always JOIN counsellors and use `c.counsellor_name ILIKE '%Name%'`.

**RULE J3.** When joining counsellors to student_remarks for call metrics, ALWAYS use LEFT JOIN.
```sql
FROM counsellors c LEFT JOIN student_remarks sr ON ...
```
This ensures that counsellors with zero calls are included in the results.
- Applies to: total calls, connected calls, success rate, efficiency, any call metric per counsellor.

**RULE J4.** For conversion rate queries (e.g. application → admission), use `course_status_journeys` with CASE WHEN for both counts in a single query (see Pattern 9).

**RULE J5.** When two counts are logically independent (come from different tables with no shared row context), NEVER join the tables to compute them together. Use correlated subqueries in SELECT or a CROSS JOIN of two single-row CTEs.

**RULE J6.** ALWAYS use `ILIKE '%Name%'` (with leading and trailing wildcards) when filtering by a person's name. NEVER use `ILIKE 'Name'` (no wildcards) — stored names include first+last name so an exact match will return zero rows.

**RULE J7.** When a query starts from a child table (`course_status_journeys`, `student_remarks`, `latest_course_statuses`, `student_lead_activities`) without JOINing `students`, ALWAYS add `WHERE student_id IN (SELECT student_id FROM students)` to guard against orphaned test-lead records that were deleted from `students` but remain in child tables. Failure to do this will inflate counts with invalid data.

**RULE J8.** **Preserve Outer Joins.** When using a `LEFT JOIN` to show a full roster (e.g., "all universities" or "all counsellors"), never put a filter for a child-table column in the `WHERE` clause. Put those filters inside the `ON` condition or use a `CASE WHEN` in the SELECT. Using `WHERE` on a `LEFT JOINED` table column will accidentally turn it into an `INNER JOIN` and hide entities with zero counts.

Example of correct LEFT JOIN preservation:
```sql
-- CORRECT: Filter in ON clause
FROM counsellors c
LEFT JOIN students s ON c.counsellor_id = s.assigned_counsellor_id 
    AND s.current_student_status = 'Pre Application'

-- WRONG: Filter in WHERE clause (turns LEFT JOIN into INNER JOIN)
FROM counsellors c
LEFT JOIN students s ON c.counsellor_id = s.assigned_counsellor_id
WHERE s.current_student_status = 'Pre Application'  -- This hides counsellors with no Pre Application students
```

### TIMEZONE RULES

All `created_at` columns store UTC. User expects IST (UTC+5:30). `CURRENT_DATE` is in IST.
**Case 1 — Explicit day boundary (today / yesterday / specific date):**
```sql
WHERE created_at >= (CURRENT_DATE - interval '5 hours 30 minutes')
  AND created_at <  (CURRENT_DATE + interval '1 day' - interval '5 hours 30 minutes')
```

**Case 2 — Rolling interval (last N days / months):**
```sql
WHERE created_at >= CURRENT_DATE - interval '30 days' - interval '5 hours 30 minutes'
  AND created_at <  CURRENT_DATE + interval '1 day' - interval '5 hours 30 minutes'
```
Always apply the `- interval '5 hours 30 minutes'` IST offset even for rolling intervals.

**Case 3 — `callback_date` column (type DATE):**
```sql
WHERE callback_date < CURRENT_DATE   -- overdue
WHERE callback_date >= CURRENT_DATE  -- upcoming
```
NEVER apply timezone offset to `callback_date`.

**Case 4 — Hour extraction (IST):**
```sql
EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Kolkata')
-- or equivalent:
EXTRACT(HOUR FROM (created_at + INTERVAL '5 hours 30 minutes'))
```

**RULE TZ1.** Always apply `- interval '5 hours 30 minutes'` IST offset to any `created_at` date boundary filter. No date filter = no timezone adjustment.

**RULE TZ2.** NEVER alter the user's specified time interval value. If the user asks for "last 6 months", write `INTERVAL '6 months'` exactly. Do NOT subtract timezone offset hours from a duration (e.g. do NOT write `INTERVAL '5 months 24 days'` instead of `INTERVAL '6 months'`). ALWAYS use `CURRENT_DATE - interval 'N ...' - interval '5 hours 30 minutes'` form — never `NOW() - INTERVAL 'N ...'`.

**RULE TZ3.** **PostgreSQL ORDER BY Alias Limitation:** In PostgreSQL, a column alias defined in the SELECT clause cannot be used inside expressions, functions, or CASE statements in the ORDER BY clause. It can only be used directly as a simple reference. This limitation applies specifically when the alias is derived (computed via CASE, functions, etc.), not a physical column.

**Example of the error:**
```sql
-- WRONG: This will fail in PostgreSQL
SELECT 
    CASE 
        WHEN EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Kolkata') BETWEEN 0 AND 5 THEN '12 AM - 6 AM'
        WHEN EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Kolkata') BETWEEN 6 AND 11 THEN '6 AM - 12 PM'
    END AS time_slot
FROM student_remarks
ORDER BY MIN(time_slot);  -- ERROR: cannot reference alias in aggregate function
```

**Solution:** Repeat the full expression in ORDER BY or use a subquery/CTE:
```sql
-- CORRECT: Repeat the expression
SELECT 
    CASE 
        WHEN EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Kolkata') BETWEEN 0 AND 5 THEN '12 AM - 6 AM'
        WHEN EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Kolkata') BETWEEN 6 AND 11 THEN '6 AM - 12 PM'
    END AS time_slot
FROM student_remarks
ORDER BY CASE 
    WHEN EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Kolkata') BETWEEN 0 AND 5 THEN '12 AM - 6 AM'
    WHEN EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Kolkata') BETWEEN 6 AND 11 THEN '6 AM - 12 PM'
END;

-- CORRECT: Use a subquery
SELECT time_slot, COUNT(*) 
FROM (
    SELECT CASE 
        WHEN EXTRACT(HOUR FROM created_at AT TIME ZONE 'Asia/Kolkata') BETWEEN 0 AND 5 THEN '12 AM - 6 AM'
    END AS time_slot
    FROM student_remarks
) sub
GROUP BY time_slot
ORDER BY time_slot;
```

If your ORDER BY logic becomes complex, using a subquery or CTE is the most maintainable and scalable approach. Relying on alias reuse in complex queries can lead to unexpected failures during migrations (e.g., MySQL → PostgreSQL), so avoid it in production-grade SQL.

**RULE TZ4.** Whenever a query returns a date or timestamp to the user, ALWAYS convert `created_at` or `updated_at` to IST using `AT TIME ZONE 'Asia/Kolkata'` (or equivalently `+ INTERVAL '5 hours 30 minutes'`). NEVER display raw UTC timestamps to the user. Additionally, ALWAYS use `MIN(created_at)` when selecting a representative date for an event from append-only tables (e.g. `course_status_journeys`, `student_remarks`) — never use `MAX` or a raw undeduped `created_at` for this purpose.
```sql
-- Correct: display date in IST
SELECT MIN(created_at) AT TIME ZONE 'Asia/Kolkata' AS event_date_ist
FROM course_status_journeys
WHERE course_status = '<Status>'
GROUP BY student_id;
```
